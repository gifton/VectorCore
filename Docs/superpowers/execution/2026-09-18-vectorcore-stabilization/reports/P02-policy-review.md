## Default-route alternatives

**A: default CPU fallback delegates to P01's validated single-query worker; Gram becomes explicit opt-in.** This removes the implicit Q≥8/N≥256 numerical method switch for supported optimized Euclidean/cosine calls. It aligns batch fallback with the single-query dispatch contract after one exhaustive batch preflight. It deliberately changes existing eligible batch scores, possible membership/ties, work and allocation. It does not establish exact-real nearest neighbors or a speed improvement. Existing callers depending on Gram behavior need an explicit migration, and gate tests must verify the selected policy rather than preserve an obsolete implicit route.

**B: preserve implicit Gram/default, add an explicit direct opt-out.** This preserves today's default numerical and routing behavior before any tiling change, and gives callers a way to request the single-query reference. It retains the silent size-dependent distinction for callers who do not opt out, so documentation must identify the gate and Gram cancellation limitation. Adding an opt-out alone does not bound default Q×N materialization. If default Gram is then tiled, B preserves the arithmetic family, not proven bitwise scores/membership from the previous full-matrix call.

For either choice, provider precedence is already correct in `Operations.swift:182–186`: BatchKernelProvider gets the original whole batch/k/metric before CPU GEMM. Its default in `BatchKernelProvider.swift:55–64` uses that provider's scheduler and findNearest witness. Provider outputs/error identity remain authoritative; no CPU accuracy or workspace promise can cover arbitrary overrides. Root must state whether a new policy means only CPU fallback behavior (compatible with current precedence) or explicitly bypasses providers (a separate breaking decision). A plain ComputeProvider's sequential setting currently controls scheduling, not Gram eligibility. The existing Q4/Q5,N300 tests do not test the actual Q8/N256 gate; both override and inherited default-loop sentinels must run at eligible shapes.

## What the direct reference actually means

`Operations.findNearest` has several observable score routes. For k<N, optimized512/768/1536 Euclidean selects squared range-kernel scores and formats square roots afterward; cosine512 uses fused top-k; dot512 uses negative-dot selection. Cosine768/1536 retains the full-score fused computeDistances path under P01. Generic small-k will use the actual supplied metric through provider.parallelReduce, exactly N calls and no AutoTuning calibration; generic large-k and optimized full-score fallback retain their established calibration/admission behavior. k≥N follows full-score paths rather than the k<N optimized top-k route. Consequently, “direct” must name this route family, not promise universal metric.distance bit parity or a common root-score admission law.

Batch delegation must preserve P01's custom metric witness, score bits, NaN-last/index ties, k clamping, original provider k and throwing cancellation/order contract. Avoid re-entering the public single-query validation for every query; use the approved private validated worker only after whole-batch checks. Exact parity fixtures must use the same metric, k, provider and scheduling context. Nested E02 execution suppresses additional library workers; do not assume independently scheduled public single-query runs have identical internal partition/calibration observations without checking the accepted implementation. This task must not alter E06's independent BatchOperations snapshot/configuration or nonthrowing completion law by implication.

## Gram tiling is not an exactness mechanism

`MatrixDistance.swift` packs Float rows, computes Float squared norms, then SGEMM with alpha−2, followed by `(cross + queryNorm) + candidateNorm` and negative clamp for Euclidean. Cosine normalizes owned rows via N01, then uses alpha1 SGEMM and clamps1−dot. NaNs survive those comparison clamps. Near-equal large-offset vectors can lose discriminating distance information before selection; adding query norm, omitting it as a ranking constant, or reranking only retained Gram winners cannot guarantee the direct winner.

A1×1 output tile still performs a GEMM dot reduction whose dimensions, leading dimensions and backend algorithm can differ from the full Q×N call. It does not become direct coordinate-difference Euclidean arithmetic, and does not prove the old reduction order/FMA/rounding. Query-only tiling, candidate-only tiling, and1-query/1-candidate tiling have no source-established universal bit-parity guarantee. Recomputed norms/normalization should use the accepted per-row routine if preserving that part of the contract, but this alone cannot fix GEMM variability. Chunking the dimension axis would add a further cross-term accumulation-order change and needs its own decision; output tiling alone should keep fullD reductions.

A bounded explicit Gram mode can promise its named Float Gram algorithm and ranking of the scores actually produced, with deterministic numeric/NaN/index selection given those scores. It cannot promise tile-size-independent bits, ties or membership without stronger algorithm control and evidence. Root must decide whether tile planning is part of the observable numerical contract. Independent analytic/Double near-neighbor fixtures establish the limitation and desired direct outcome; exact accepted-kernel controls establish only the measured fixture parity. No tolerance may silently excuse a membership-law change claimed as bitwise preservation.

## Logical workspace accounting

Let r be active query rows, c candidate rows per tile, D dimension, K=min(k,N), and let h be the logical heap entry bytes for the chosen representation. Current TopKBuffer has separate Float scores and Int indices, so its scalar payload is K·(Float.stride+Int.stride), not necessarily the padded stride of a result struct. NearestNeighborResult has Int+Float; use its actual MemoryLayout stride when modeling result storage.

For serial Euclidean tiles with both sides packed, the basic concurrently live payload is:

`Float.stride * (r*D + c*D + r + c + r*c) + r*K*h`

This covers both packs, both norm arrays, the cross-term/distance tile reused in place, and r retained heaps. Cosine can omit persistent norm arrays if normalization is performed in-place with scalar planning, but both normalized owned packs and the output tile remain. Neither expression includes extraction/sort temporary arrays or final output yet. Current extractors construct retained pair arrays plus TopKResult index/distance arrays before mapping to NearestNeighborResult; an implementation using them must count those actual overlapping buffers, or deliberately remove them with separately checked equivalent selection. Array COW/accidental shared mutable buffers can add copies. No promised cap may be justified by an optimizer merely shortening lifetimes.

With r=c=1 the basic Euclidean model still contains twoD packs, two norms, one score and a K heap. A cap below the selected minimum feasible plan must produce a defined typed failure before allocation/kernel work, not silently revert to unbounded direct or Gram work. Candidate tiling inside a query tile bounds heaps to rK but repacks candidates for each query tile. Packing allN candidates once instead has a persistent Float payload N*D+N in Euclidean and requires that minimum budget before any query tile fits. Inverting loops to pack each candidate tile once while retaining heaps for every query trades repacking for QK state. These are concrete work/memory alternatives, not free reuse.

Parallel active tiles multiply private packs/norms/tile/heaps by their actual simultaneously outstanding worker bound, unless some packs are demonstrably shared immutable inputs and counted once. A per-worker budget cannot be called a per-operation cap. E02/P01 worker bounds and nested suppression must be reflected in planning. Provider-created fan-out and backend-internal buffers are outside a library-managed workspace model.

A narrowly honest cap is a **checked upper bound on named library-managed temporary element payload for this CPU operation**. It must identify included array capacities/counts and extraction buffers, whether reusable prepared inputs count, aggregate worker accounting, and explicitly exclude allocator headers/slack, ARC/task/runtime costs, caller inputs, BLAS-internal memory and RSS. Reserved Array capacity may exceed a requested capacity, so distinguish counted requested/logical slots from actual allocation bytes. Measurements can validate observed allocations separately; they cannot turn this formula into a hard RSS/allocator cap. The exact public name/shape remains root's decision.

## Returned storage and preflight

The nested public result necessarily contains Q*K result elements plus Q row handles and the outer handle/storage. k≥N means Q*N returned elements even if scratch is tiled. Clamp k before capacities and check products/bytes; an Int.max k must not directly drive allocation. If returned payload is excluded from a temporary-workspace cap, say so prominently and still preflight its representability. If root instead includes results, reject any cap smaller than unavoidable output plus simultaneous minimum scratch. Full matrix APIs similarly require Q*N scalar output and nested reshape may overlap an additional flatQ*N matrix; bounded search scratch does not repair that distinct API-24 cost.

Keep existing public Operations validation order: positivek, nonempty queries/candidates, every query dimension, every candidate dimension, then cross-set equality, before provider or CPU work. New Gram planning must additionally check positiveD where required, LP64 dimensions/leading dimensions, each pack/norm/tile/heap/output element and byte product, row/index offsets, and range endpoints before subtraction/conversion. Check total logical candidate indexing independently of Int32 BLAS tile sizes; do not impose the pointer selector's current Int32 candidate ceiling on a new Int-indexed route by accident. Conversely, tiling away large BLAS n does not make unchecked global output products safe. Unsafe custom UnifiedVectorBuffer byte/lifetime obligations cannot be validated from scalarCount alone; don't expand the public conformance contract implicitly.
