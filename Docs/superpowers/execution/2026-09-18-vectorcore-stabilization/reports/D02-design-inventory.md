## Actual override surface and factory/storage contracts

`Operations.bufferProvider` occurs only at its declaration in Sources. `VectorCore.configuration` is an immutable default `Configuration` value, with stored batch configuration and alignment fields, and no operational reader. E06's actor-backed BatchOperations.configuration/updateConfiguration is a separate, now effective control. These are not aliases; do not document mutations of a copied global facade as changing execution. Removing/deprecating or expressly reserving the unused facade/buffer binding is a root contract choice; wiring allocation into the hook would expand lifetime/error and performance scope.

Active overrides have different scopes: `Operations.computeProvider` controls Operations execution and gives BatchKernelProvider first dispatch; `Operations.simdProvider` is an array-provider override used by elementwise VectorCoreOperations/VectorMath and named Operations methods, not every scalar/vector/kernel operation. `Operations.linearAlgebraProvider` is consumed by PCA. Static Float/Double providers and direct batch kernels are independent. A precise symbol/entry-to-hook table and local concrete/generic/existential/provider spies can be verified in Core without pretending a sibling/GPU executed.

`Vector<D>.Storage` is explicitly `DimensionStorage<D, Float>` regardless of `D.Storage`. StaticDimension nevertheless requires a VectorStorage associated type described as the optimized storage, and many extensions use only `D.Storage: VectorStorageOperations` as an availability gate. Production occurrences are in ConvenienceInitializers, VectorOperationsProtocol, NaNInfinityHandling, VectorMath, VectorNormalization, VectorEntropy and VectorCoreOperations. Existing test/probe generic constraints also occur in O03AllocationProbe, NumericalPolicyContractTests, NormalizationRangeContractTests and StorageAllocationContractTests. Removing that associated-type requirement and these gates would broaden extension reachability for custom dimensions even though actual storage remains unchanged. It requires explicit custom-dimension compile/runtime controls and full reachable numerical/shape tests; it is not a comment-only change. Keeping a misleading customization hook is not an implemented storage policy. Inventory all public built-in `Dim*.Storage` aliases separately before any removal.

VectorTypeFactory deliberately returns generic Vector<Dim128/256/384/512/768/1536/3072> and DynamicVector for other nonnegative dimensions. Existing concrete cast tests are meaningful. No evidence here supports switching those results to specialized Vector*Optimized types, which would change routing/casts/overload selection. Descriptions of “optimal” selection and optimized SIMD storage should identify these actual types and DimensionStorage's accepted ownership/storage behavior. `VectorCore.createVector(data:)` is a nonthrowing force-try convenience over the checked factory; its malformed-input contract needs explicit documentation if retained, not a claim of typed-error propagation.

VectorProtocol's required hooks include storage/count, array/repeating/default constructors, array extraction, unsafe scoped borrows, isFinite/isZero and inherited Collection/Codable/Hashable requirements. Arithmetic/normalization/distance extension methods are largely static helpers rather than dynamic protocol witnesses; VectorFactory separately supplies requirements. S02/N01 already repair concrete/generic shape and numerical policy classes. Full universal bit equality across distinct reduction implementations is not implied. D02 must distinguish intended customization requirements from static convenience methods, with an external conformer and method-spy matrix. Do not promote every convenience method into a protocol requirement merely because static dispatch exists.

## Device metadata

ComputeDevice is currently a preference enum, not a discovery abstraction. CPU availability always returns true; GPU availability tests only compile-time Metal import/simulator and ignores every index; neural availability tests a positive CPU count on supported Apple OS versions. GPU capabilities use hard-coded1024 parallelism and unified-memory true; neural uses hypothetical16/float16/int8. availableDevices can thus publish neural/GPU while createProvider returns nil for both; mostCapable prioritizes them. No other production consumer of these query/recommendation properties was found in the scoped search.

Root needs to choose an honest CPU-only supported-provider status or a separate explicit/injected discovery API. Unknown hardware presence must not become false physical absence, and compile-time framework import must not become successful hardware discovery. Keeping enum cases for downstream labels does not require Core to create a GPU/Neural provider. Alignment/minimum-size constants are advisory guesses, not universal requirements or measured break-even boundaries; a naming/documentation choice must precede change. An immutable test discovery value, if selected, should cover nonexistent/negative indices and no-neural states without actual unavailable hardware. No Metal/Neural runtime acceptance is established here.

## Exported C declarations and integer accumulation

The umbrella VectorCoreC.h exports implemented feature queries, FP32 dot/L2/range512 and generic INT8 dot, plus the included LAPACK header. Its long following “proposed” section declares unimplemented symbols. The normal Swift module does not establish those symbols link. Moving proposals into a non-public design document is a supported-surface decision, not implementation of them. A generated declared/defined symbol manifest plus an ordinary C/C++ linked consumer should exercise every retained implemented declaration; coordinate LAPACK declarations with accepted L01. Existing range bodies and Swift wrapper write compact output0..<(end-start), contrary to the header's out[start..end) wording. Retain actual compact indexing and add nonzero-start/offset/sentinel controls.

INT8 fixed widths through1536 have an exact signed32 worst-product bound1536*16384=25,165,824. Generic131072 terms of(-128)*(-128) reach2^31. Scalar C uses signed int32 addition; the NEON final horizontal result plus scalar tail and x86 tail also use ordinary signed C additions. Swift's C-off fallback explicitly wraps with &+=. Thus a portable generic-lane policy must be chosen before broader support: one candidate is an explicitly defined modulo2^32 result interpreted in the Int32 range, preserving the Swift fallback and fixed-width exactness. This would require unsigned accumulation/tail/final combination and an explicit safe uint32-to-signed numeric mapping, not reliance on a signed-overflow flag. SIMD hardware additions and loop endpoint arithmetic need their own source audit. Current loops use i+16/32/64<=lanes; a remaining-count formulation can avoid size_t addition wrap without giant allocations, but requires a bounded pure boundary test and exact existing tails.

A potential reference matrix can include lane0,1,15/16/17,31/32/33,63/64/65, fixed widths and131071/131072/131073 plus mixed signs/cancellation. Small bounded buffers suffice for the overflow witnesses. Independent Int64 references can cover those finite test sizes and then map explicitly to modulo32 if that policy is approved. Ordinary exported dispatcher, actual scalar and supported architecture implementations should be distinguished; cross-compilation is not execution. UBSan on actual scalar/tail sources can establish the language-level overflow repair. No x86/SDOT execution has occurred in this investigation; all-architecture acceptance may require actual supported runner evidence later.
