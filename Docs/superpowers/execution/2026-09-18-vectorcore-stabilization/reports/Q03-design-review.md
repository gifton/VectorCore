# Q03 independent design review

**Verdict: ACCEPT.** Read the candidate brief, complete MixedPrecisionDiagnostics recording/state implementation and the three FP32 constructor hooks plus their shared recorder in MixedPrecisionKernels. Inspected constructor consumers, including SoA builders that invoke these constructors. No builds, source edits or delegation were performed.

## Concurrency and snapshot contract

The existing scalar and batch unlocked isEnabled guards are real races against locked enable/disable; synchronizing the hint alone does not fix those commit paths. The proposed one-lock policy covers enabled, counters and finite-range initialization. Preparing classification outside the lock is safe when the original/output values are immutable and enabled is checked again at commit. A single locked batch merge gives coherent snapshots relative to reset/toggle. Accepting a pre-reset preparation into the new generation is explicit and implementable without extra epoch machinery.

A false preflight hint may skip preparation even if a later enable occurs. This does not conflict with commit-time acceptance for records that actually reach commit, but documentation/tests must preserve that qualification rather than claim all conversions occurring while enabled are counted. Repeated enable resets, disable preserves the snapshot, and reset preserves enabled. Formatting/logging from captured values after unlocking avoids OSLog work in the state critical section. Per-field saturating nonnegative counters are sufficient; tests checking sums near saturation must use widened/checked arithmetic rather than overflow while asserting coherence. A seeded state must still exercise the actual production merge.

## Classification and range

Actual constructor-produced UInt16 bits are the correct classification input. Float magnitude thresholds cannot distinguish 65505 from 65520 or tiny nonzero values from representable subnormals. Finite-input signed-infinity output is overflow; input infinity contributes only to total; finite nonzero signed-zero output is underflow; exponent-zero/nonzero-fraction output is subnormal. Input NaN has its own category. This partitions the exceptional events without relabeling source infinity or zero as arithmetic failure.

The three constructor hooks have immediate access to original SIMD lanes and final storage, so they can record actual output without changing the conversion kernel or recomputing an assumed representation. Raw FP16 initialization and reverse conversion must remain non-recording. SoA builders already call these constructors for real vectors: their conversions are therefore naturally recorded through the same hooks; padding zeros created as raw storage are not extra conversion events. Do not add a second SoA recording hook that double-counts them. Public low-level conversion functions are outside the three-hook coverage claim and should not silently gain global recording.

Finite range initialization needs private observed-finite state rather than totalConversions, since a NaN/infinity prefix is valid. First finite input initializes both bounds. Signed-zero ties require explicit sign handling in both local batch reduction and merge with an existing snapshot; ordinary min/max tie behavior is not a sufficient deterministic contract. A range summary must distinguish no finite inputs from a finite zero. Empty batches are a useful zero-event control alongside nonfinite-only batches.

## Oracle, isolation and sanitizer evidence

An independent integer-rounding oracle/table must establish both output bits and event classification at the three rounding boundaries, both signs and Float neighbors. The specified ties are correct: 2^-25 ties to zero, 2^-14 - 2^-25 ties to the least normal, and 65520 rounds to infinity under round-to-nearest-even. Tests should compare output bits first, then compare full counters against an independent category table; diagnostic agreement with itself is not evidence of correct conversion. No NaN-payload preservation promise is needed.

Per-instance record tests provide exact totals without changing the singleton. Real constructor scenarios must run in fresh filtered children so unrelated conversion suites cannot increment/reset their totals; construct any expected vectors or reference FP16 values before enabling, or use raw-bit expected fixtures so oracle setup does not itself invoke instrumented constructors. Snapshot checks must not perform extra diagnostic-generating conversions between reads. Parent probes should be explicit no-ops and require child body/result/completion markers, preventing an empty filter from masquerading as coverage.

Run the original concurrency baseline only as its own bounded TSAN child/probe, retain whether a race was actually reported, then run the repaired instrumented fixture separately. Use the same instrumented executable for child work, preserve TSAN environment and nonzero/report evidence, and avoid running the unsafe baseline concurrently with unrelated validation. An instrumented parent whose child silently uses an unsanitized binary would not satisfy the plan. Every worker/gate must complete before final snapshot assertions and process exit; use finite test synchronization and the stated outer deadline/cleanup. If sanitizer startup prevents body markers, report setup limitation rather than a clean race test.

Stable enabled intervals establish exact direct/constructor counts. During toggles, validate whole-batch snapshot possibilities and nonnegative bounded counters under the documented acceptance policy, not an invented exact accepted total. Source review remains required for every state access even after a clean sanitizer run.

No contract contradiction or omitted required recording route found. Hardware detection, profiler synchronization/statistics, numeric kernels, public precision routing and performance targets remain outside this bounded design. Final acceptance requires actual frozen boundary/constructor/concurrency evidence and explicit TSAN outcome, as the brief states.
