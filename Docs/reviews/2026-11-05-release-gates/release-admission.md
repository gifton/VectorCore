# Exact-candidate release admission

This is a concrete qualification sequence for the remaining 0.4.0 gates, not release approval. It preserves the existing platform and compiler policy pending an explicit decision. The investigation source is `27a045dd648c01a4ef9c5d8d36c5afc92f36f6fb`; every future execution must record its actual source rather than inherit that identity.

1. **Choose a distribution-compatible compiler tuple.** Record exact compiler/frontend hashes, selected SDK, target triple, language/optimization flags and runtime. Use the unchanged `Docs/reviews/2026-11-04-release-phase-one/compiler/run.py` against each accepted native compiler tuple, including its omitted-write negative controls. The positive observations must be correct even where the ordinary test suite records a known issue. A release cannot be admitted from `CI Required` alone. The advertised Xcode 27.3 beta remains exploratory until tested; a beta result would not qualify a different released binary or establish submission eligibility.
2. **Freeze one candidate and test its consumers.** Run the full normally enabled Debug/Release suites with both frameworks accounted for, public documentation programs and downstream contracts using the accepted compiler. For source SwiftPM distribution, test the compiler actually used by consumers. For a separately designed binary distribution, qualify producer and importer combinations, including generic/inlinable specialization; producer-only tests do not isolate downstream code from compiler defects.
3. **Apply the chosen platform coverage requirements.** The platform matrix separates existing required CI combinations from recommended runtime evidence. Preserve deployment floors separately from executed runtime versions; decide which remaining minimum-OS, Intel, tvOS, visionOS and representative-device combinations are necessary to substantiate the release's compatibility claims, then exercise them or explicitly approve and document narrower limits. Record architecture and real test body outcomes. Physical iOS tests need an app-hosted harness or signed public-consumer app: the current tool-hosted Swift package setup cannot run there. A new platform execution on a numerically rejected compiler remains useful evidence but cannot close compiler acceptance. Reconcile selected and broader sanitizer workloads, every skip, runtime warning and the bounded leak experiment without claiming whole-project leak freedom.
4. **Qualify performance on a suitable host.** Settle source/compiler/products before measurement. Apply the reviewed host-readiness rule after competing work ends and preserve any failed admission; this rule is the task-local investigative protocol, not a pre-existing public support policy. Keep the existing strict identity, correctness, case-selection, median/per-unit and 5% comparison rules. Use the complete predetermined repeat schedule and retain every result. Record current thermal/power and interval-load observations with explicit continuity limits. A successful local repeatability comparison is neither an old-to-new performance verdict nor acceptance of another compiler.
5. **Run hosted acceptance for that exact candidate.** The previous successful hosted run used `f779d92`, before 64 later executable-input file changes present in `27a045d`. Rerun the applicable required matrix, inspect underlying numerical observations and skips as well as job status, and retain source-bound artifacts. Recheck a clean downstream resolution/build from the proposed release reference.
6. **Finalize the release materials and integration.** Reconcile release notes, version, support wording, claim-ledger section handling and the accepted limitations with actual evidence. Only then cut the separately agreed 0.4.0 release branch and perform the separately agreed merge/tag/publication. This investigation changes no release tag, public version or support policy.

The order prevents the same expensive qualification from being repeated against several moving candidates. Platform inventory, skip classification, tool validation and measurement preparation can proceed while compiler acceptance remains open; final release acceptance cannot.
