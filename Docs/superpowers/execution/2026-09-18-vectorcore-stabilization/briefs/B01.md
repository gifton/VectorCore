## Accept the existing empty DynamicVector frame

Change the shared header's dimension domain to0...10000. A zero-dimensional frame is exactly16 bytes with the ordinary header and CRC. DynamicVector.decodeBinary returns the valid empty value. Empty Data remains insufficient data. Fixed Vector<D> decoding retains exact D.value equality after header/CRC validation, and its existing constructor/dimension obligations remain unchanged; a valid empty frame must reject for every supported positive fixed dimension. Do not special-case an empty frame by skipping checksum or frame-length validation.

Keep validation order: minimum length, magic, version, dimension cap, flags read, exact total length, CRC, destination dimension, payload. Trailing bytes and concatenated frames remain invalid; preserve the existing insufficientData classification for an exact-size mismatch even when too long. Dimension10001 still encodes through the existing nonthrowing VectorProtocol encoder but is rejected at decode; this asymmetry is an explicitly documented existing limitation, not a promise of arbitrary-count checked encoding. Do not increase the cap or convert encodeBinary to throwing incidentally. BinaryHeader.init's existing representable nonnegative-dimension precondition remains outside the bounded empty repair; public validated decoding never supplies an unbounded payload allocation.

Version1 reserved flags remain ignored when the CRC/frame are valid, including nonzero bits. Encoders emit zero. No flag meaning is assigned and no new rejection is introduced. Version values other than1 remain invalid; do not pretend migration exists.

## Specify the bytes and concrete precision contracts

Document numeric magic0x56454354 separately from its little-endian wire bytes54 43 45 56. Do not change those bytes to ASCII VECT. The complete layout is UInt32 magic at0, UInt16 version at4, UInt32 dimension at6, UInt16 flags at10, N UInt32 Float bit patterns at12, then UInt32 CRC, all little-endian; total16+4N. CRC uses reflected polynomial0xEDB88320, initial/final xor0xffffffff over header plus payload. It is corruption detection, not authentication.

Publish a full independent golden frame, including CRC, plus empty/special-bit fixtures. An offline Python generator using explicit integer packing and zlib.crc32 is allowed; cross-check its CRC with a simple independent bit-at-a-time reference and the known123456789→0xCBF43926 vector. Generated Swift byte/word tables must not import/call Core writers/CRC to form expectations. Compare every emitted byte and decoded Float.bitPattern. Preserve old nonempty goldens unchanged while adding empty support.

Document/test the actual representation matrix: generic Vector<D> JSON uses an elements object and same-type binary decode; DynamicVector JSON uses dimension/elements and supports empty JSON/binary; four optimized FP32 types use concrete array JSON and common FP32 binary encoding into explicit DynamicVector or matching generic Vector<D> destinations; three INT8 types use validated storage/quantization-parameter JSON and common dequantized FP32 binary encoding of16+4N bytes into those FP32 destinations. INT8 binary is not compressed storage preservation. Raw FP16 structs have no direct Codable/VectorProtocol binary API; the supported explicit toFP32 then encode path serializes already-rounded values. It cannot recover pre-rounding FP32 or promise arbitrary FP16 NaN payload preservation.

Binary FP32 storage must preserve exact original signed-zero, infinity, subnormal and NaN words without arithmetic on fixture inputs before encoding. JSON's default nonfinite rejection and optional explicit string strategy are separate tests; the latter preserves classification, not NaN payload bits. Test concrete optimized/INT8 Codable implementations, not generic Vector aliases or extracted arrays under an optimized test name. Exact ordinary Float roundtrip expectations must match the selected representation; never use a tolerance helper that accepts NaN against finite input.

## Binary protocols remain explicit consumer extension points

Select the documented-extension-point option from SER-05: do not add retroactive built-in conformances in this task. Core vector methods alone do not satisfy generic BinaryEncodable/BinaryDecodable constraints. Replace the misleading illustrative Vector conformance with a complete consumer-owned wrapper example implementing the protocols and delegating to a named built-in vector's methods. Describe encode-only versus same-concrete roundtrip methods separately from protocol adoption. No new optimized/INT8 same-type binary decoder is introduced.

CoreProtocols.swift has a distinct default on VectorType where Self: BinaryEncodable that throws outside1...10000. Preserve that existing checked default and explicitly document its domain versus the nonthrowing VectorProtocol method. Do not expose competing defaults by adding conformances without a witness decision. A narrow documentation-only edit to this file is authorized. External Swift6 fixtures exercise a consumer-owned BinaryCodable wrapper (including concrete, generic and existential encoding plus generic decoding) with default/removed-last empty DynamicVector behavior. Separate negative typechecks show bare built-in Vector/Dynamic/optimized/INT8 do not conform merely because a method exists. An explicit consumer VectorType conformer using the checked default, if included, must test its positive-domain rejection rather than inherit the empty-vector wrapper contract accidentally. No downstream generic failure is claimed to have existed.

The public documentation must make this choice clear enough that callers can write a working adapter. It is a deliberate API disposition of an integration opportunity, not an implemented built-in conformance feature. If later downstream intent requires built-in adoption, that needs its own default-witness/cap compatibility decision; it is not blocked on a hidden change in B01.
