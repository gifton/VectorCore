**Source SwiftPM rebuilds with the consumer's compiler.** A qualified producer build cannot pin that compiler for downstream source users. A source-policy allowlist must identify exact accepted compiler/build/SDK/platform combinations and independently check the numerical observation; `swift-tools-version: 6.0`, `compiler(>=...)` and an aggregate green result do not express that allowlist.

**Prebuilt artifacts do not remove the client compiler from the contract.** `Sources/VectorCore/Vectors/Vector.swift` declares public generic `Vector<D: StaticDimension>` and marks initializers, subscript and other bodies `@inlinable`; `VectorProtocol.swift` also exposes inlinable generic operations. Swift's [library-evolution guidance](https://www.swift.org/blog/library-evolution/) explains that clients can see such bodies and inline or emit specialized copies. Consequently producer and importer/compiler combinations need separate qualification, as do client-created pointer/Array/closure shapes. Existing pure-Swift canary failure is independent of linking VectorCore. Enabling module stability/library evolution is a packaging/compatibility choice, not evidence of numerical safety; this repository currently declares source targets, not a binary distribution. No generic/inlinable removal, public API change or ad hoc noinline workaround is proposed.

For all options, explicitly resolve macOS arm64/Intel, minimum macOS runtime, iOS simulator versus device and minimum runtime, tvOS, visionOS, and Catalyst where claimed. Existing compilation results cannot stand in for these runtime cells. WatchOS and Linux remain outside advertised support. Sanitizer scope, GPU consumer integration and performance gates remain separate from these compiler probes.
