# Q02 unchanged baseline coverage mapping

The baseline library was built with `swift build -c release --target VectorCore --enable-code-coverage --jobs 6` in its separate coverage scratch. The retained ordinary source hashes equal the exact baseline sources. Linked fixture compilation uses `-O -swift-version 6 -parse-as-library -D Q02_BASELINE -profile-generate -profile-coverage-mapping`; exact argv, linked object/module hashes and binary are in `coverage-before-01/provenance.json`. This instrumentation is solely work-count evidence. Ordinary allocator/time measurements use the separate uninstrumented before-02 binary.

`coverage-control` compiles an independent three-call function with the same compiler coverage flags. Its exported function entry count is exactly three; the program checks its result equals nine. This validates count interpretation without a tuner hook.

Each fresh baseline selection at dimensions 512/768/1536 and candidate counts 50/500 has these actual exported **function entry** counts: dimension-specific executeStrategy 125; benchmarkStrategy 5; computeFP32Baseline 1; generateTestVectors 1. The five kernel-invocation buffer closures each have 25 entries. Source regions for the generator vector loop count N+1; those are **region execution counts**, not additional generator calls. `mapping.json` retains the exact mangled functions, old source coordinates and all regions. `kernel-callsite-mapping.json` retains the five closure entries per workload. The N=1 mapping/raw/merged/export is retained separately in coverage-before-01.

At each old executeStrategy body, the query-FP16 standard/blocked cases each have one query constructor and one SoA builder; the two query-FP32 cases each have one SoA builder. Their case/closure counts are 25 each. Therefore the measured source callsites account for 50 query constructor calls and 100 SoA builder calls per selection. These are source callsite counts; no claim is made that inlined constructor machine-code function entries exist. The independently locked Q03 diagnostics report exactly `25 * (4*N + 2) * dimension` converted elements for every workload. Converted elements are not constructor-call counts.

The single FP32 reference is separate from the 25 full-FP32 strategy invocations. Five warmups and twenty measured invocations per each of five strategies explain the 125 execute entries on these fixtures; no fallback rerun occurred in them. This does not infer work counts from elapsed time and does not generalize tuning quality.

Raw `.profraw`, merged `.profdata`, complete llvm-cov exports, binary/source/object provenance and bounded command exit records are retained. Original initial SwiftPM build logs were removed by external temporary-file cleanup; the snapshotted build description, actual linked objects, compiler invocation and all coverage runtime/export logs remain. This limitation does not manufacture a missing build log.
