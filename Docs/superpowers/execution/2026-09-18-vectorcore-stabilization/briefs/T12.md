# T12 brief: FP16 range-kernel hot-path allocation, and FP16 conversion pins (root-created; from V04 phase D, T09 and phase F)

## Findings
- V04 D4: `aos-fp16-reused` makes 262,145 timed-window allocations per invocation (64 × 16 B per candidate). D2 shows `swift_slowAlloc(16)` in `range_euclid2_mixed_core` next to `fp16ToFp32_simd8` (an inference, labelled in the benchmark notes). Hot-path heap allocation in an FP16 distance kernel.
- NaN payload encodings are unpinned: no test checks the quiet-NaN result. Defining `-DNATIVE_FLOAT16_SUPPORTED` leaves all 7 FP16DiagnosticsBoundaryTests passing (phase F fix-1 M-5/M-8).
- `convertBatchNEON` converts with native Float16 and its tail with the software converter, so NaN payload bits can differ within one buffer (0x7fc12345 → 0x7e09 vs 0x7e00).
- The software FP16 converters have only approximate Float16-free decode coverage. An exhaustive host-independent test is feasible (T09 review).

## Required
1. Root-cause the 16-byte allocations with evidence (emitted code, allocation probe), then remove the per-conversion heap allocation without changing arithmetic results. Prove bit-identical outputs on finite, exceptional and range fixtures, and show the allocation count drop with the V04 D4 probe method.
2. Add an exhaustive, host-independent, Float16-free software-converter test:
   - all 65,536 decode patterns against an exact bit-widening reference;
   - round-trip identity for non-NaN patterns;
   - RNE midpoint ties for encode.
3. Pin the NaN encodings. Decide and document ONE NaN policy for scalar, batch and NEON conversion (canonical quiet NaN 0x7E00, or payload-preserving), make all paths agree, and test it. A behaviour change needs a CHANGELOG entry.
4. Decide on the dead `NATIVE_FLOAT16_SUPPORTED` scalar branch: delete it, or keep it under the item-2 and item-3 tests (coordinate with D02).
5. Re-run the V04 D4 FP16 probe and update the resolved boundary notes and ledger entries (boundary identity changes are expected and must be stated).
