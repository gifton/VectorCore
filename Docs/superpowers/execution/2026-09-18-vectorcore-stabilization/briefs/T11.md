# T11 brief: benchmark correctness-gate policy (root-created; from V04 phase D and final review)

## Findings
- Generic `batch.euclidean2` cases record maxRel 1.04e-06 to 2.31e-06 against the fixed 1e-06 FP32 threshold at all widths (V04 phase D, final-fix re-review F-1). As a result the documented CI comparison recipe ALWAYS exits 2, because a non-empty `failures` array is not waivable, so it cannot detect regressions on this tree. Workaround documented: `--exclude 'batch.euclidean2.*.generic.*'`.
- Matrix diagonal relative errors: the zero-reference relative-error class. A relative error against a zero reference is undefined, and the gate flags it. This is the SECOND instance (phase C matrix, plus the consumer-only entries), so it needs a mechanical closure in the correctness metric.
- `noop` (and other cases without validation) records "Missing validation".

## Required
1. Root-cause the generic euclidean2 excess. Is it accumulation-order error growth with D/N in a scalar generic path versus an FP32 reference, or a reference/tolerance mismatch? Derive the expected error bound for the actual summation (for example γ_n·Σ|terms|), and set a principled per-case or per-route threshold from it, with the derivation in a comment that names a test. A blanket loosening is NOT acceptable.
2. Zero-reference class: define the correctness metric for near-zero references (absolute error with a stated floor, or a mixed rel/abs criterion). Add negative and positive controls, and a mechanical test that the gate never computes relative error against |ref| below the floor.
3. "Missing validation": decide per case whether validation is required. Cases that cannot be validated (noop) declare that explicitly instead of failing.
4. After the fix, the documented CI recipe without `--exclude` must exit 0 on this tree. Update Docs/Performance_Guide.md's known-issue note and the claim ledger.
5. Evidence: before/after failure lists; Debug and Release BenchmarkContractTests; Python suites; ledger at 0 problems.
