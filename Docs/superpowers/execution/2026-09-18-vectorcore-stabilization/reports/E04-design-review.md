## Ownership and Swift 6

The actor-pool borrowed model and MemoryPool owning-handle model are consistent and intentionally different. Actor pools must retain authoritative allocation records until release/destruction; handles do not extend owner lifetime. Clear removes only cached records. Destruction frees active and cached allocations once; a destruction test with surviving borrowed metadata must never dereference it. Fresh identities on reuse and validate-before-remove prevent stale or forged metadata from retiring a genuine lease. Matching only address or requested count would not implement this design.

Replacing TypedBufferPool's raw return/release API with an immutable borrowed handle is an appropriate breaking change; the current raw pointer cannot identify acquisition generations. A handle storing only immutable address/count/identity metadata can cross isolation without asserting that Element or its pointee is Sendable. The synchronous actor-isolated scoped closure permits nontrivial values constructed and destroyed within the body, while Sendable captures/results enforce the intended crossing boundary. Unsafe pointer escape remains a documented caller restriction, not a compiler guarantee. Actor teardown access to metadata may require a narrowly reviewed low-level ownership wrapper; the brief explicitly permits that rather than demanding a blanket actor suppression.

Provider scoped release must retain the provider through the body and the awaited release. Explicit do/catch handles success, body error and cooperative cancellation without detached cleanup. OperationContext's current deferred Task is a real reachable completion-order defect and is correctly included. Existing BufferPoolContext single/multiple-buffer helpers already await release and must preserve that ordering while adopting fresh identities. Multiple-buffer acquisition must not accidentally turn partial setup into an untracked lease path; current acquisitions are nonthrowing, and their fatal failure policy is explicit.

MemoryPool's weak pool link and handle-owned allocation preserve late handles. The handle must carry the allocation's actual capacity/alignment/deallocator through reuse, not replace that metadata with the weaker latest request. Caller deinitialization duties are necessary for both borrowed and owning handles; raw allocation/free balance alone cannot prove generic payload destruction.

## Domains, accounting and allocation

The physical-versus-logical distinction resolves zero-count requests: physical minimum allocation counts toward retention even when logical count is zero. Admission-only strict cache caps avoid the current fresh-return burst problem and require no workload target. Active/cached accounting, zero budgets, per-size limits and clear semantics are sufficiently specified. SwiftBufferPool's disabled diagnostic counters are separated from operational accounting; widened hit-rate computation avoids the existing public-initializer sum overflow.

Checked power-of-two rounding must reject the first unrepresentable bucket, not return an undersized one. Counts/products/MB conversion/alignment/configuration policy and named Release-active guards cover the current reachable invalid domains. Recoverable acquire failure must leave no allocation stranded. In MemoryPool, allocation occurs outside the lock today: any final accounting admission check must be repeated while locked, and a failed commit must free the newly allocated block with its matching deallocator. Cached-byte updates and independent bucket recomputation must occur under that same lock; diagnostics may saturate, operational counters must not.

The scoped failure injector must distinguish pooled allocation, first direct aligned fallback and final raw fallback. Assert allocator-entry order/count, actual alignment, matching frees and body/error behavior, rather than infer a fallback from the returned result. Binding fresh raw bytes and explicit lifetime extension of a pooled handle through normal/error completion address the existing source defects. Real OOM is correctly excluded from recoverability claims. Portable allocation family pairing and no unexecuted Linux claim are appropriate.

Timer policy preserves current explicit-cleanup meaning while disabling nonpositive/nonfinite automatic intervals. The positive finite horizon check must bound both interval conversion and addition to the current monotonic deadline; checking only conversion is insufficient. Source and boundary tests can establish that without long sleeps or a scheduling redesign.

## Evidence and boundaries

The actual Release allocation profile supports replacing the return-time flatMap scan with maintained cached bytes: requested bytes grow with cached entries in three repetitions. It does not establish a contention bottleneck or a speedup target. The final repeated linked probe must retain remaining bookkeeping allocations honestly. No workload or downstream performance decision is required to repair measured work amplification.

The proposed allocation identity ledger, scoped failure injection, nontrivial payload lifetime tests, stale-generation tests, cap tables, late-handle checks, named child diagnostics, Debug/Release/ASan and public Swift 6 consumers form an adequate bounded acceptance matrix. Validate real forced failures and release-before-return ordering, not only synthetic statistics. Consumer evidence should include both explicit typed handles and scoped APIs; negative captures must fail at the intended concurrency boundary. No VectorAccelerate runtime or GPU claim is implied by its adapter source inspection.

Apart from the two concrete clarifications above, no contradictory ownership policy, missing reachable production route, or compatibility blocker was found. Existing O05/Q02 surfaces remain outside scope, and no new performance goals or routing activation are proposed.
