# R05 — Explicit metric-aware relevance scores

Root contract. API-11 closure candidate. R01 is accepted; schedule after R02 because both own VectorCollection.swift's search producer. Reserve SearchResult.swift against S03. Breaking source changes are authorized; no downstream build or workload decision is required to repair the score pole.

## Design and observable behavior

The distance remains the value produced by the requested DistanceMetric witness and is the sole input to existing TopK ranking. Relevance is an optional additional interpretation. No metric name/type recognition may replace a witness, no score may change membership or distance ordering, and no score is a calibrated probability.

Add a defaulted DistanceMetric requirement `func relevanceScore(for distance: Scalar) -> Scalar?`. The default returns nil: an unknown/custom metric has no implicit relevance mapping. A conformer may supply its own interpretation and must document its domain/range. This requirement enables existential witness dispatch; an extension-only method would silently lose a custom implementation. Do not change distance or batchDistance requirements or numerical kernels.

Built-in Euclidean, cosine, Manhattan, Chebyshev, Hamming and Minkowski metrics use the existing inverse-distance convention only for finite nonnegative distances: `Float(1 / (1 + Double(distance)))`. Signed zero is valid and gives1. Negative or nonfinite values return nil. The builtin output for the finite domain is in(0,1], including a positive representable result at Float.max. Cosine deliberately retains this inverse-distance convention; do not silently relabel it as cosine similarity or change it to1-distance. Keep Minkowski's configured p witness unchanged.

DotProductDistance uses the logistic interpretation of its negative-dot distance: score=1/(1+exp(distance)). For finite d>=0, compute t=exp(-Double(d)), score=Float(t/(1+t)); for finite d<0, compute t=exp(Double(d)), score=Float(1/(1+t)). This avoids exponential overflow and has no pole at d=-1. Finite Float extremes may round to0 or1; the documented range is[0,1], weakly decreasing with distance. No strict monotonicity claim survives all Float rounding/saturation. Any nonfinite distance returns nil, rather than representing an invalid calculation as confident relevance.

SearchResult.score remains an optional explicitly stored Float and retains its existing initializer/Codable fields. Explicit values are preserved exactly, including unusual ranges/nonfinite bits; built-in score guarantees do not apply to values supplied by callers or custom witnesses. Remove the metric-free `computedScore` property and replace it with `computedScore(using metric: any DistanceMetric<Float>) -> Float?`. It returns an existing score without invoking the metric; otherwise it calls the supplied relevanceScore witness exactly once. The caller must provide the metric that gave the stored distance. Missing context is represented by nil, never by guessing a metric from distance sign or name. Migration: use `.score` for a producer-populated score or call `.computedScore(using: theMetric)` when the interpretation is known. No additional serialized metadata is needed.

The actual default collection search producer and R02's SimpleVectorCollection snapshot search must populate each selected result's score using the same metric instance/witness that computed its distance. Evaluate relevance only for selected results, once each. Call metric methods outside the collection lock, preserving R02's reentrant snapshot behavior. Generic/custom metric defaults produce nil. Convenience searchEuclidean/searchCosine/searchDotProduct continue forwarding their existing metric. TopKResult-to-SearchResults conversion lacks metric context and continues to leave score nil; mapIDs and Codable preserve an explicitly stored score rather than recomputing it.
