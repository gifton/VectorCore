## Ownership and lifetime

PoolAllocation is a final checked-Sendable owner with immutable integer address, physical capacity/bytes, actual alignment, deallocation family and Sendable allocator boundary. Its final reference releases exactly once through the matching allocator family. It owns raw storage, not initialized generic values. This is a defensible narrow metadata contract and does not claim that pointee access is synchronized or Sendable.

The three actor pools retain owner references in active leases and cached buckets; public/internal borrowed handles retain only immutable capability metadata. Actor destruction releases both collections. Clear releases cached storage only. Release checks UUID, requested count and actual address before removing the active record or changing counters. Reuse creates a new UUID; stale/foreign/duplicate or forged metadata therefore cannot retire the current lease. Typed handle creation and identity/address are not publicly mutable. Cache keys are sufficient because each storage instance has a fixed element layout and alignment.

MemoryPool preserves its distinct owning-handle behavior. A live handle owns PoolAllocation and weakly references the pool; late destruction frees directly through the owner if the pool is gone. A successful return transfers an owner reference into the cache before handle destruction releases its reference. Reuse preserves actual alignment and byte/capacity metadata. Fresh allocation is bound to T before exposing a typed pointer; cached typed storage stays partitioned by ObjectIdentifier(T). Caller initialization/deinitialization duties are documented and the String/reference fixtures exercise them separately from raw frees.

The MemoryPool allocation operation occurs outside the bookkeeping lock, with a second checked accounting commit after allocation. A concurrent accounting failure releases the temporary owner without publishing a handle. No deallocation-family mismatch or dangling ownership transfer was found.

## Arithmetic, budgets and fallback

Negative requests and invalid alignment are rejected before allocation. Power-of-two rounding checks each multiplication; exact-count pools check stride multiplication; logical zero uses one physical element/byte. Alignment validation short-circuits before alignment-minus-one arithmetic. Nonthrowing failures use named guard/fatalError diagnostics that survive ordinary Release.

Active bytes are checked before actor acquisition mutates cache state. Return admission uses remaining-cap subtraction and actual physical bytes, including zero-count storage. Per-size caps and SwiftBufferPool maxBufferSize remain independent admission constraints. Operational accounting is maintained even when optional diagnostics are disabled; cumulative counters saturate and public hit-rate addition is widened. MemoryPool maintains cached bytes on reuse, return and cleanup; its independent scan is test-only and the old return-path full-cache scan is absent. Byte totals bound the relevant bucket-count sums because every allocation has positive physical size.

MemoryPool.withBuffer validates once and keeps the pooled handle or fallback owner alive across the complete body and unwinding. Both forced fallback stages preserve requested alignment and bind fresh storage; aligned allocation uses free and Swift raw allocation uses deallocate. Failure injection is per instance and final ordinary tests use actual allocations, not the baseline malloc_logger hook. Real final-stage exhaustion remains explicitly nonrecoverable.

Timer setup rejects nonfinite/nonpositive intervals and values at/beyond its chosen Int nanosecond horizon before conversion, then checks uptime addition and integer conversion. Explicit cleanup retains the configured age-cutoff meaning. Tests cover disabled domains and an enabled ordinary interval; this review does not claim a wall-clock timer-firing experiment.

## Scoped APIs and Swift 6

BufferProvider.withBuffer is async throws because acquisition may independently throw. It invokes no body/release after acquire failure and awaits one release on success or thrown body error. There is no detached cleanup or asynchronous defer. The provider remains referenced through release. Cooperative cancellation propagates after release, while a cancellation-ignoring body retains the lease until completion.

TypedBufferPool.withBuffer executes a synchronous throwing body on its actor, with Sendable closure/result requirements; defer releases synchronously. The unsafe pointer nonescape obligation is documented as a caller contract, not a type-system guarantee. OperationContext now matches BufferPoolContext's awaited do/catch cleanup.

Positive public fixture covers the exact provider documentation example and nonisolated, actor and MainActor callers with a nontrivial String payload. Negative fixtures target non-Sendable captures/results and the intentionally removed typed raw-handle/default-budget interface. Compile/run evidence still needs association before final acceptance. The final implementation report should explicitly preserve the source migration: supply maxCachedBytes, use the new Handle's pointer/buffer, then release that Handle; downstream borrowed adapters must retain their Core provider until release. No downstream runtime claim follows from these sources.
