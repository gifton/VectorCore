# P02 — Explicit CPU batch search and bounded Gram workspace

Root-approved design after independent review; dispatch only after accepted prerequisites. Read WORK_ITEMS P02, the current P02-design-inventory.md and P02-policy-review.md, and approved P01. Breaking changes are authorized. Requires accepted P01, V02 and V04 in addition to R01/R03/N01/E06; refresh their actual source and evidence before implementation. API-25 consumer-owned contiguous inputs and TOOL-10 production-scale acceptance remain staged under the user's deferred downstream intent and targets. This brief does not invent a borrowed-buffer API or modify a sibling.

## Selected route and alternatives

Choose a single-query-compatible CPU default for Operations.findNearestBatch. The old implicit Q>=8/N>=256 Gram gate changes numerical method and temporary storage solely because the batch grew. Keeping that default with an opt-out would leave the distinction for ordinary callers. The new default instead calls P01's private validated single-query worker per query after the existing whole-batch validation. This is a deliberate numerical/performance compatibility change, not an exact-real arithmetic or speed claim.

Retain Gram search as explicit opt-in with caller-selected tile geometry and a checked logical temporary-payload limit. Tiling alone does not repair Gram cancellation. Do not rerank only the retained candidates and claim direct-neighbor equivalence. Neither full-matrix nor tile-size-independent bit parity is promised. Keep the dimension axis whole; no partial-D GEMM reductions.

The existing public MatrixDistance convenience/prepared APIs remain available with their documented ownership and unchecked caller preconditions. This task does not replace their public contracts or introduce zero-copy ownership/lifetime promises. Their internal per-row normalization/norm/packing arithmetic may be reused by the new checked route.

## Public CPU policy and provider precedence

Add a public Sendable `BatchSearchCPUStrategy` enum with exactly:

```swift
case perQuery
case gram(queryTileRows: Int, candidateTileRows: Int,
          maximumTemporaryPayloadBytes: Int)
```

Add `cpuStrategy: BatchSearchCPUStrategy = .perQuery` as the final parameter of Operations.findNearestBatch. This policy describes only Core's CPU fallback. Keep existing validation order: positive k, nonempty query/candidate collections, every query dimension, every candidate dimension, then cross-set equality. An installed BatchKernelProvider still receives the original whole batch, original k and metric before any CPU strategy validation/planning. Its output and original error remain authoritative. The CPU policy, including its budget, does not constrain or bypass that provider. Document this explicitly and test a provider with otherwise infeasible/invalid CPU-only options. A scheduling-only ComputeProvider still selects how the per-query fallback executes.

`.perQuery` delegates to P01's private validated worker through the accepted provider scheduler. Do not call the public findNearest repeatedly, revalidate the entire candidate set, calibrate a new tuner or change P01's score routes. The reference is public single-query Operations.findNearest under matching metric/k/provider context: optimized Euclidean k<N squared-score admission, direct512 dot/cosine, retained fused full-score cosine768/1536, generic metric witnesses, and k>=N full-score paths remain distinct. Preserve current NaN-last/smaller-original-index laws and returned score bits on each route. Custom callback cross-range ordering stays unspecified. No claim that all routes equal metric.distance or exact real arithmetic.

`.gram` supports only EuclideanDistance/CosineDistance with concrete512/768/1536 optimized arrays, as the former implicit route did. Unsupported metric/type combinations throw VectorError.unsupportedOperation before CPU allocation/kernel work; no fallback silently disregards the requested algorithm/budget. Explicit Gram supports small Q/N too, so re-derive and test newly reachable Q1/N1 and partial tiles. No new global configuration field, provider requirement, automatic crossover or parallel Gram scheduler.

## Checked tile plan and memory boundary

After provider delegation has been ruled out, validate Gram tile requests >0 and temporary limit >=0 as invalidConfiguration with named fields. These simple field-domain errors precede unsupported CPU type/metric admission; admission in turn precedes full plan/representability/budget checks. All of these errors precede the first CPU cancellation check. Preserve this order when multiple inputs are invalid. Clamp positive requested tile rows to actual Q/N before products, so Int.max requests are acceptable when the actual clamped plan fits. Let r=min(queryTileRows,Q), c=min(candidateTileRows,N), D=dimension and K=min(k,N). The geometry is caller-selected: do not silently shrink tiles to fit. A valid plan whose temporary payload exceeds the supplied cap throws resourceUnavailable with required/allowed byte context before any packing, normalization, heap/result allocation or BLAS call. No fallback on budget failure.

Use one synchronous active query tile at a time, scanning candidate tiles in increasing index order. Reserve/reuse at most r query rows, c candidate rows, an r*c Float score tile and r TopKBuffer heaps of capacity K. Repack candidate tiles for each query tile; this repeated work is explicit, not a reusable-input performance claim. Query packing occurs once per query tile. Cosine normalization modifies only these owned scratch rows. Euclidean norms retain the existing Float row-norm routine and postprocess order `(cross + queryNorm) + candidateNorm`. Cosine retains N01 normalization and comparison clamps. Preserve selected NaNs and Euclidean squared-score admission followed by NaN-preserving root formatting.

The per-operation logical temporary-element payload is:

`Float.stride * (r*D + c*D + r*c + (euclidean ? r+c : 0)) + r*K*(Float.stride + Int.stride)`.

This counts all requested logical slots in both packs, Euclidean norm arrays, score tile and every simultaneously live heap. There are no active Gram workers multiplying this formula. Scalar locals and container/runtime/allocator metadata/slack, BLAS internal allocations, caller inputs and final returned result storage are excluded. It is not an allocator-byte, live-memory, RSS or deadline cap. Name the boundary in API docs and error context; never describe this proxy as a hard memory cap. Ordinary Array allocation/COW may exceed requested logical slots, which actual allocation evidence must report separately.

The implementation must not create additional uncounted full score, pair, index, distance, slice-copy or sort arrays. In particular, do not call an extractor that materializes K pairs plus TopKResult plus mapped results while claiming the formula above. Add a narrow internal mutating TopKBuffer `drainWorstFirst(_ consume: (Int, Float) -> Void)` if needed. Heapify once at entry (including a partially filled heap), then repeatedly consume the root index/value, replace it with the last live entry, decrement size and restore the heap. The synchronous nonescaping consumer fills the final K-result row from the end to the start. Empty performs no callback; the buffer ends empty and can be reused. This avoids repeated O(K) heap building on every removal. Preserve direction/tie policy, original score bits and value-copy independence. No temporary sorting array, changed public comparator, pointer Int32 selector or third merge buffer. This addition requires mechanical full/partial drain-and-refill tests against an independent sorted oracle, not just P02 smoke coverage.

Final output is Q rows of K NearestNeighborResult values and is excluded from the temporary cap. k>=N therefore still returns Q*N records. State this prominently. Clamp k before allocation and separately check result element/byte counts, row-container counts/bytes and every pack/norm/tile/heap count/byte sum before work. Use actual MemoryLayout strides. Check positive D and LP64 D, active r/c and all BLAS leading dimensions before conversion; total Q/N indexing need not fit Int32 when their tiles do. Pure planner tests must cover representability without constructing huge collections. Check additions/products/range-end and offsets, not only the final byte total. No arbitrary production-size ceiling.

Use fixed planned scratch capacities with explicit active row counts for partial tiles. Do not pass the whole allocated capacity as the active BLAS row count. A padded score stride may use planned c; initialize/read/write only actual active coordinates and retain sentinel padding tests. Do not slice Array inputs to create tile vectors. Retain full-D row copy bounds and caller-valid UnifiedVectorBuffer bytes. Existing concrete optimized input ownership remains unchanged; do not add escaped raw pointers across await. All scratch borrow scopes are synchronous.

## Throwing search cancellation

After the complete CPU Gram plan and cap succeed, call Task.checkCancellation before scratch or output allocation. Check again at each query-tile and candidate-tile boundary, after the actual tile computation, before allocating/draining each finalized query result row, and before returning the full result. Cancellation throws CancellationError and exposes no partial output. A cancellation arriving after the final check does not retroactively invalidate a returned result. No async suspension or new worker fan-out is required to observe the task cancellation flag.

Individual synchronous packing/normalization, allocation, BLAS calls and heap-drain operations are not interrupted mid-operation. There is no hard cancellation-latency or memory-release deadline; tile geometry and k influence work between checkpoints. `.perQuery` inherits the accepted P01/E02 throwing provider cancellation behavior, and installed BatchKernelProvider witnesses retain their own behavior. The separate nonthrowing pairwise API keeps its complete-result law.

Add pre-cancelled valid-CPU-plan controls that prove no packing/BLAS/scratch or output construction, plus cancellation triggered by a real tile observer after actual work and before publication. Both throw without partial results. Add already-cancelled invalid-domain/unsupported/infeasible fixtures to pin the stated validation precedence; no instrumented substitute kernel is an execution oracle. A post-final-check race cannot be made a hard timeout assertion.

## Pairwise matrix reshape disposition

Repair API-24's redundant flat N*N-to-nested-rows GEMM reshape in the existing BatchOperations.pairwiseDistances result, without adding a new public matrix container or flat API. In the eligible GEMM helper, prepare candidates once, then allocate each final N-element row and compute one query row directly into that row with the existing MatrixDistance prepared/into path. Euclidean formatting happens in that same row before it is appended. The returned nested matrix still contains N*N values, but there is no separate full N*N score matrix logically live alongside it. Do not merely add an unused alternative while retaining the old reshape in this route.

This changes SGEMM call geometry from a full N*N multiply to N one-query multiplies, so off-diagonal bits and potentially rounding/ties may differ. Record that numerical and performance migration honestly; do not claim universal bitwise equivalence. Preserve actual metric diagonal rewrite, the existing pairwise Euclidean NaN-to-zero off-diagonal formatting, cosine comparison behavior, and generic/non-GEMM arithmetic. Retain E06's one snapshot, eligibility, configured minimum N and actual `batch.pairwise.gemm` phase observation. This entry stays nonthrowing and complete-result under cancellation. Its output/packs and MatrixDistance preconditions remain separate from the new throwing Operations Gram workspace policy.

Do not modify the generic N100 row scheduler, symmetry/callback behavior, nested execution law or non-GEMM routes. Update only the adjacent E06 configuration comment to describe independence from the new Operations CPU policy. Existing pairwise large-offset/exceptional controls must identify the new call geometry rather than imply equality with the old full-matrix kernel. Measure the added per-row BLAS-call cost alongside the avoided reshape allocation; no speed improvement is required or presumed.
