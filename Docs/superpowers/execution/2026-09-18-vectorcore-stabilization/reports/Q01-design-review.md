## Assessment

The proposed common affine operation, zero-inclusive calibration, finite cap for newly calibrated tuples, preservation of valid legacy fields, scale-cancelled cosine, and transactional mutable borrow form a coherent bounded contract. ## Calibration and endpoint bound

The finite projection cap is justified directly: with integer zero point z in [-128,127], D=max(abs(-128-z),abs(127-z)) is between 128 and 255. Choosing a positive Float s no greater than Double(Float.max)/D ensures every legal code's real projection has magnitude at most Float.max. Computing the cap in Double and correcting an upward Float rounding with nextDown is appropriate. Multiplication here is exact in Double: a Float significand has at most 24 bits and D at most 8 bits. A rounded Double division that lies microscopically above its exact cap cannot let an unsafe Float through the correction: if it equals a Float, its distance from the true cap is far smaller than the spacing between distinct Float-product values near Float.max. If desired, remove that proof obligation by verifying Double(candidateScale)*Double(D) <= Double(Float.max) directly and stepping down otherwise.

A useful real-arithmetic argument supports the proposed one-step target, independently of random sampling. For nonzero asymmetric calibration write s0=(hi-lo)/255, a=-lo/s0, b=hi/s0, so a,b>=0 and a+b=255. If z=round(a-128), put e=z+128-a, |e|<=1/2. Code endpoint distances are A=a+e and B=b-e. Without a cap, clipping loss is at most half a step. With cap s=M/D, D=max(A,B), M=Float.max, and m=M/s0>=max(a,b), the upper-end deficit in units of s is b*D/m-B (and analogously the lower). If D=B it is nonpositive; if D=A its maximum is attained by m=max(a,b), yielding at most 255*|e|/max(a,b)<=1. The lower endpoint is symmetric. Symmetric calibration has s0=maxAbs/127 and D=128, giving at most one capped step at the positive endpoint. Interior nearest rounding contributes at most half a step; saturation uses the endpoint deficit rather than adding another half step to it.

This is NOT yet a complete proof of the actual Float/Double algorithm: Float rounding of s0, Double zero-point division/rounding, clipping classification, final Float projection, and the clamp to leastNonzeroMagnitude remain to be included. In particular, do not cite the above argument as an implemented universal bound. A reasonable brief can require the stated finite regression tolerance while separately describing the exact-arithmetic motivation.

Specify the tolerance as an executable expression, for example s + 2*ulp(x) + 2*ulp(decoded), all widened before addition. The phrase “two Float ULPs of the input and decoded endpoint” otherwise admits different interpretations. Define ulp via finite spacing/exponent, including the least-subnormal floor; abs(x.nextUp-x) is infinity for x=Float.max and would make an extreme regression vacuous. Assert finite tolerance as well as finite decoded output. Clarify whether the guarantee is only calibrated endpoints or every input in the calibration interval; arbitrary out-of-range inputs necessarily only have a saturation guarantee.

Recommended independent fixtures:

- Exact powers-of-two scales with representable half-integer code thresholds; test the threshold and Float neighbors, positive and negative, including saturation boundaries. Expected codes must be stored/closed-form, not computed by the new production helper.
- Signed zero, +/-leastNonzeroMagnitude, the largest subnormal and smallest normal with their neighbors, constant positive/negative intervals, one-sided intervals, and mixed-sign intervals.
- Symmetric [-Float.max,Float.max], [0,Float.max], and [-Float.max,0], explicitly checking all 256 raw code projections. For s=Float.max/128 exactly, code -128 projects exactly to -Float.max, while positive saturation is deliberately short.
- Asymmetric intervals near changes of rounded zero point, including a/b near 127.5/127.5, and endpoints at Float.max with unequal opposite tails. Exercise both sides of a scale cap transition and power-of-two scale rounding transition.
- Subnormal examples with independently evident answers: asymmetric [0,MIN] uses s=MIN,z=-128, giving code -127 for MIN and -128 for zero; [-MIN,MIN] has ideal z=-1 by nearest-away, s=MIN, and endpoints -2/0. These cases intentionally use only a small fraction of byte capacity.

Zero-inclusive constants solve the existing positive/negative constant collapse without an arbitrary tiny fallback. The larger interval can reduce resolution for narrow ranges far from zero; record this intentional new-calibration behavior. Zero is exactly representable for newly calibrated tuples. Original min/max metadata must remain distinct from the augmented interval and must not be used to reject legitimate raw codes. All-zero s=1,z=0 is unambiguous; explicitly choose how min/max signed-zero bits are retained.

## Conversion and legacy tuples

Source confirms separate Float reciprocal AoS and SoA conversions, scalar Float division, and a Float/FMA decode path currently diverge. One shared observable Double divide/add/round-away/clamp operation closes that class. The maximum finite Float / minimum positive Float is below 2^277, so Double intermediates stay finite even with an Int32 offset. Round before integer conversion and clamp while still floating; Int32 subtraction must also be widened before subtraction in cosine/decode.

The shared operation should define ties according to its computed Double intermediate. It should not promise exact-real rational rounding for every possible legacy tuple: adding a large integer offset can affect values extremely close to a tie. Test exact known ties rather than deriving expected outputs through the same floating formula.

Legacy decode validation proposed in the candidate is appropriate: finite positive scale, finite ordered metadata, and symmetric=>zeroPoint0. Preserve asymmetric Int32 extrema and exact serialized values; do not infer that metadata bounds every stored code or that an asymmetric offset must lie in byte range. Include legacy fixtures with zero points Int32.min/max and values beyond Float's integer-exact range, distinguishing mathematical Double decoding from final IEEE Float projection. Check scalar/toFP32/SIMD helper agreement by Float bits, including overflow infinities.

SoA padding should equal scalar quantize(0), not raw code zero. A legacy zero point outside byte range cannot encode exact zero; document that padded lanes are excluded by logical vectorCount. Retain tests for candidate counts 1,2,3,4,5 so a conversion repair cannot turn padding into a real candidate. Empty entry points should still validate explicitly supplied parameters and any mode/domain argument before shortcuts.

## Cosine and bounds

Scale cancellation is valid for positive finite scales for both symmetric and asymmetric tuples. For built-in widths the symmetric integer sums have absolute bound 1536*128^2=25165824, below Int32.max and therefore also Int64.max. This includes code -128, which should appear in fixtures despite the nominal symmetric [-127,127] calibration description. Do not extend the bound to arbitrary custom laneCount.

For asymmetric Int32 offsets, every centered code is an exactly representable integer in Double with magnitude at most 2147483775 (<2^32). Individual products are below 2^64 and 1536-term squared sums below 2^75; norm products are likewise far below Double overflow. Products need not be exact because they can exceed Double's 53-bit precision. Compensated accumulation improves summation but does not make those products exact; set an explicit finite residual/error tolerance. Centering in Double avoids signed Int32 overflow. Either zero norm preserves distance1. New asymmetric and legacy-offset tests should include self/opposite where representable, differing scales, orthogonal/cancellation patterns, and one/both zero vectors.

An independent oracle should multiply centered codes by original scale in Double and accumulate decoded-coordinate products independently. Those coordinates are below 2^160; squared sums below 2^331, safely finite. Include a valid legacy tuple whose Float projection is infinity but Double oracle cosine is finite, to ensure the new route never detours through toFP32. For the most cancellation-sensitive fixtures use exact integer dot/squared-sum constants computed independently (Python arbitrary integers or stored constants), rather than reusing the implementation's centered-code summation. Report absolute cosine/distance error near zero; relative error is unsuitable at an orthogonal result.

## Mutable borrow

Transactional-on-throw matches the current successful-only writeback structure and avoids quantization during unwinding. The proposed three-width mechanical matrix should compare original raw storage AND parameter bits/fields after throw; retained-copy isolation alone misses replacing both values with equivalent recalibration. Throw the same identifiable error after writing NaN/infinity, and assert that error survives unchanged. On normal return validate every temporary element before publishing a replacement; reject explicitly rather than relying on try! to convert a constructor error into a generic trap.

One important migration detail: a valid legacy vector may initially project to Float infinity. A successful no-op borrow then fails the finite-result policy, whereas a throwing borrow still rolls back and rethrows. This follows from the candidate but needs explicit documentation/coverage, or a consciously different policy. Also successful no-op borrows can change scale, symmetry and raw codes through recalibration; transactional does not mean bit-preserving on successful return. No additional behavior change is requested by this review.

## Remaining root decisions / recommendations only

Distribution calibration needs a named percentile definition. Since output is symmetric, an absolute-magnitude percentile is a simple defensible choice: finite p in (0,100], choose nearest-rank magnitude with rank ceil(p*n/100), clamp to the valid rank domain, and calibrate [-threshold,threshold]. Alternatively central coverage with equal tails is valid but different, and must be specified with small-array examples. Validate p and all payload elements before sorting or empty shortcuts. In either design avoid converting a rounded Double(Int.max) endpoint directly to Int: branch at the upper boundary or use an integer-safe index bound. Test p=100, smallest positive p, 50, default99.9, NaN/infinities, and tiny arrays. Current source's min=sorted[n-safeIndex], max=sorted[safeIndex-1] can reverse endpoints, independently of integer-conversion failure. Do not silently choose semantics in an implementation worker.

Choose a canonical empty calibrator/SoA result and strategy treatment explicitly (for example all-zero metadata/s=1/z=0), including direct public calibrateParams([]). perDimension single-vector calibration should reject before empty handling as proposed. These are recommendations, not additional approved behavior.

EX-04 is still reachable and merits a separate bounded task or explicit deferred limitation. Source reasoning gives simple future witnesses, not runtime reproductions: two equal raw nonzero vectors with scales 1 and 1.nextUp satisfy the current approximate gate yet have nonzero decoded Euclidean distance; scale products around 2^-150 can round to zero before multiplication by a large integer dot; mixed Float squares can underflow for representable tiny distances or overflow for large but representable distances. Correctly admitting subnormal calibrated scales increases practical reachability. An exact-scale gate repair sends more inputs to the currently unsafe mixed fallback, so it cannot by itself justify Euclidean closure. Likewise fixing scalar decode changes fallback values without proving range-safe accumulation. Root should ledger the limitation or assign a coherent widened-metric repair; this review does not authorize it or broaden Q01 to the entire quantization subsystem.

## Final-brief review — dispatch blocker

Reviewed the complete briefs/Q01.md, this earlier review, EX04-provenance.json and EX04-results.log, plus the current scalar/SoA fallback source. The retained root evidence records compile/probe exit0, frozen module/object hashes, and 21 observed metric failures against the accepted O04 Release module. I did not rerun that compiled probe. The now-approved EX-04 extension is consistent with the gate-reachability concern: it explicitly replaces both lossy INT8-to-FP32 fallbacks, widens mixed differences/squares, and adds the missing SoA capacity guard. Calibration tolerance, percentile/empty semantics, raw tuple preservation, transactional borrow behavior, exclusive writes and generic/C-backend exclusions resolve the earlier design questions.

Disposition: **BLOCKED on one concrete asymmetric-dot arithmetic contradiction**, rather than a scope or authorization concern.

The brief requires real affine decoded-coordinate semantics and allows infinity only when the mathematical result lies outside Float range. It also prescribes compensated Double decoded-coordinate products for asymmetric dot. Compensation cannot repair information already lost when forming each decoded coordinate/product. The following valid legacy fixture has exactly zero mathematical dot but the prescribed rounded products have a huge nonzero sum:

- Query: asymmetric, zeroPoint=Int32.min, scale=Float.max; first codes [-127,-126,-125], remaining codes arbitrary legal bytes (choose0).
- Candidate: zeroPoint0, scale=2^100; first codes [1,-2,1], remaining codes0. Finite ordered metadata can be [0,0] for both tuples because the brief deliberately does not require it to bound raw codes.
- Let A=2^31-127. The exact centered dot is A-2*(A+1)+(A+2)=0, hence the affine dot is zero at every built-in width.
- Independent binary64 arithmetic experiment (Python, no production Swift run): Float.max obtained from IEEE bits0x7f7fffff; compute terms `float((2**31+q)*s)*float(c*2.**100)` for q=(-127,-126,-125), c=(1,-2,1), then `math.fsum(terms)`. Result: **-1.0284403483257538e62**, which is outside Float range. Even correctly summing the rounded Double products cannot recover the exact zero. With candidate scale1, the residual is -8.112963841460668e31, also violating an exact-zero expectation without overflowing.

Requested brief correction: factor both per-vector scales out of dot, and accumulate the centered integer dot exactly before applying positive scales in Double and projecting once. Individual centered products fit signed Int64: maximum magnitude (2^31+127)^2 <2^63. Their 1536-term sum needs more than Int64 but less than 2^75; a two-word signed accumulator, a suitably available wider integer, or a separately justified exact expansion can handle this bounded domain without a third-party dependency. Another option is explicitly weakening the mathematical zero/overflow contract, but that would be a substantive numerical policy change and would permit this false infinity. Ordinary compensated Double accumulation of centered products alone also lacks exactness for all legacy offsets, so merely moving scale multiplication is insufficient for a general exact-zero promise.

Add the above fixture at all three widths with stored expected +0 (numeric zero if sign is not promised), plus a neighboring nonzero centered-dot fixture. Generate exact centered dot/squared constants with arbitrary integers independently; do not use the decoded-coordinate Double oracle alone for this case, because it reproduces the same loss. Existing independent large-offset cosine constants remain useful: cosine's absolute residual tolerance can tolerate tiny relative product error, whereas a zero dot scaled enormously cannot.

Nonblocking implementation cautions within the existing brief:

- If sharing a compensated accumulator with mixed Euclidean paths, preserve IEEE infinity deliberately; an unconditional compensation expression such as (sum-next)+term can turn an infinite positive squared difference into NaN. Include an infinite FP32 coordinate and a separate NaN coordinate in mixed scalar/SoA controls. Ordinary positive Double summation also meets the stated finite range design without this complication.
- Final metric tolerance arithmetic must widen before multiplying ULPs, as the endpoint formula already does. Keep expected-zero fixtures exact/classified; a near-zero relative bound would conceal the dot witness.
- The nearest-rank helper should branch to N-1 for an upper rounded boundary, not convert Double(N-1) blindly when N is near Int.max. The brief's artificial index controls correctly reserve this boundary.

No additional production scope, nested delegation, commits, Swift builds or runtime tests were introduced. Only the numerical arithmetic experiment above supplements this design review. Once root resolves the asymmetric-dot contradiction, the remaining bounded brief is acceptable for implementation dispatch; implementation acceptance still depends on the prescribed RED/Debug/Release/ASan evidence and independent final diff review.

### Root-selected blocker resolution — exact centered integer accumulation

Root selects an internal signed two-word accumulator (Int64 high, UInt64 low), exact signed-product addition using reporting-overflow carry/sign extension, and conversion through unsigned magnitude before Double scaling. No platform-floor dependency on Int128 is introduced. Root also proposes using exact centered dot for asymmetric cosine, with the same accumulator available for squared sums.

This design **resolves the arithmetic blocker**, subject to its inclusion in the final brief and implementation verification. Each centered coordinate is in [-(2^31+127),2^31+127], so each product fits Int64; built-in sums are below2^75 and cannot exhaust the signed two-word representation. Exact centered dot preserves the zero in the retained counterexample. The product of two positive finite Float scales is exactly representable in Double (at most48 significand bits), with range bounded by 2^-298 and 2^256. Applying it after exact accumulation and integer-to-Double conversion stays finite in Double (magnitude below2^331), then projects to Float once.

Implementation/fixture requirements within this resolution:

- Sign-extend each Int64 product into the high word; add its UInt64 bit pattern to low with carry. Test positive carry, negative borrow/sign extension, cancellation across word boundaries, and an exact final zero after large positive/negative partial sums.
- For negative totals, form the unsigned two's-complement magnitude across BOTH words before Double conversion and restore the sign afterward. Converting signed high and unsigned low directly can catastrophically cancel and must not be used.
- `Double(magnitudeHigh)*2^64 + Double(magnitudeLow)` avoids cancellation, but the two-stage conversion is not automatically a correctly-rounded integer-to-Double operation for every 75-bit integer. The brief can retain its bounded fixture tolerances, or specify guard/sticky rounding if correct rounding is promised. Do not add an unsupported exact-conversion claim.
- Retain the preceding legacy fixture as required behavioral RED/acceptance at all three widths: query z=Int32.min, s=Float.max, codes[-127,-126,-125,0...]; candidate z=0, s=2^100, codes[1,-2,1,0...]; expected exact numerical zero. Also run candidate scale1, which reveals a false finite residual rather than false infinity. For a neighboring nonzero exact-centered-dot control, change query's third code to-124: exact centered dot1; use scales yielding a representable result as well as overflow classification.
- Independently precompute exact signed sums with arbitrary integers, including near-extreme Int32 offsets and full-width repeated codes. Using the same two-word helper as the test oracle would fail the required independence. Include a negative total and totals around2^64 to exercise magnitude conversion rather than only zero cancellation.

No source edits/builds or further numerical experiment occurred for this assessment. Final acceptance of dispatch awaits inspection of the patched brief; the retained original blocker remains historical evidence rather than an outstanding objection to this selected resolution.

### Final patched brief — ACCEPT for dispatch

Reviewed full Q01.md with SHA256 `42693a280a8bab97a95ffbb423d1609d2b939fba5cb350f9caeb9b9f87f1ed5f`. It incorporates the exact signed two-word dot/squared-sum design, magnitude-first conversion, the required zero-dot counterexample, and a product-plus-FMA-residual/expansion difference path for scalar and SoA Euclidean fallbacks and mixed FP32 inputs. **ACCEPT for bounded implementation dispatch.** There is no remaining design blocker identified in this review; this does not certify an implementation or numerical closure.

The new difference refinement is necessary and mathematically appropriate. Independent arbitrary-integer evaluation confirms root's two fixtures:

- 8388609*2139095551 =17944036190978559; 8388610*2139095296 =17944036190978560. Difference=-1, but both separately rounded binary64 products equal17944036190978560.
- 8388609*2139095041 =17944031912787969, versus mixed coordinate17944031912787968. Difference=+1, again lost by separately rounded binary64 decoding. The mixed comparison value is also exactly representable as Float as stipulated in the fixture.

An exact Double product-plus-FMA-residual representation is sufficient for these products: both operands are exactly representable in Double, no finite product approaches Double overflow, and nonzero residuals lie on at least the Float least-subnormal lattice, far above Double underflow. Error-free subtraction of the expansions before rounding the difference retains the small residual that ordinary separate decoding loses. Positive Double square accumulation and final sqrt then have ample range at all built-in widths. This review checked the integer arithmetic and binary64 rounding independently with Python; it did not execute a production Swift metric or claim a repair.

Three implementation-review details remain explicit acceptance checks, not new scope or dispatch blockers:

- Centered integers can need32significand bits and Float scales24, so the full product can need up to56bits. The brief's “can require55” statement is an example rather than a tight upper bound; helper reasoning must allow56. Product-plus-residual covers it.
- “Expansion subtraction” must retain both residuals and the high-part subtraction error before final rounding; simply evaluating (aHigh-bHigh)+(aLow-bLow) without the error-free transformation is not the specified algorithm. Verify against independent exact dyadic/integer fixtures over the powers-of-two scale family.
- Nonfinite mixed FP32 coordinates need the brief's IEEE path before a finite-only error-free transform: residual formulas involving infinity can create NaN unintentionally. Include explicit infinity-only and NaN mixed controls in both scalar and SoA families. This follows from the existing nonfinite contract.

The independent ordinary-case Double oracle is appropriately limited; exact-integer/Decimal fixtures now close the important oracle-correlation gaps for cancellation. Explicit replacement of both INT8 lossy fallbacks resolves the newly reachable equality-gate routes. SoA capacity/prefix checks, legacy tuple preservation, finite new-calibration projections, transactional borrow semantics, optional C exclusions and generic metric exclusions are consistent with the owned files and approved bounded extension.
