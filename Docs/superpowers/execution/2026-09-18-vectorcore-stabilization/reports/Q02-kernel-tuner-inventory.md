## Selection, identity, precision and constraints

- Workload initialization (50–62) stores arbitrary dimension/batchSize and optional memoryBudget/latencyTarget without validation. Resource fields have no subsequent reads. Precision error percentages at 46–47 are comments, not enforced actual-data bounds.
- `hashWorkload` (592–594) is an interpolated dimension/batchSize/precision string, not a hash. Both profiles and overrides share this identity. It excludes memory/latency, hardware, operation, data, algorithm version and profiling parameters.
- `selectStrategy` (188–222) lazy-loads profiles, returns any manual override first, otherwise chooses maximum profile score when enabled, otherwise heuristic. No selected-strategy feasibility, precision, profile/workload consistency, expiry or validity filter exists. `.auto` itself is accepted as an override even though private execution rejects it (466/509/549).
- Heuristics (247–283) preserve fp32Full absent override/profile contamination; `availableStrategies` (596–612) profiles only AoS/SoA for full precision. Small batches of either reduced mode select mixed; medium/large int8Acceptable selects quantized. Unsupported dimensions and negative batch sizes still receive heuristic strategies.
- Overrides can weaken full precision. Existing `testManualOverridePersists` (KernelAutoTunerTests:114–130) explicitly sets cpuQuantized for fp32Full and expects it; “persists” here means same-process dictionary lookup, not restart persistence. Root must explicitly migrate this expectation if precision is made dominant.
- `selectMixedPrecisionStrategy` (803–820) neither consults its own selection/override nor enforces the documented high-level mixed-strategy precondition. It translates full mode to tolerance 0.0001 and delegates dimension/count/tolerance to MixedPrecisionAutoTuner.shared, allowing that tuner's independent override/calibration policy. This is the explicit NUM-20 route, not evidence that ordinary heuristic selection quantizes full mode.

## What profiling actually measures

`profileWorkload` (291–325) generates synthetic data once and benchmarks 2/3/4 strategies according to precision; it caches nonempty results and saves. `generateTestData` (614–680) supports only 512/768/1536, uses dimension-specific seeded values in [-1,1], and eagerly constructs FP32 candidates, FP16 candidates, INT8 candidates and an INT8 query regardless of selected precision. These live simultaneously.

`benchmarkStrategy` (329–407) runs default 10 warmups plus 100 timed executions per strategy. Time uses mach_absolute_time on Darwin or ContinuousClock elsewhere. Timings include each executeKernel call and result-array work; synthetic generation and eager reduced conversion are outside this measured interval. Each strategy then performs an additional untimed AoS baseline and target execution for accuracy (710–737). There is no cancellation checkpoint, explicit admission budget, or workload limit here.

`executeKernel512/768/1536` (427–555) measures dot products only. AoS maps FP32 dot kernels; mixed maps preconverted FP16 candidates with an FP32 query; INT8 uses preconverted candidates and query. SoA calls the *candidate-array convenience wrapper*, which rebuilds SoA and allocates output on each execution (BatchKernels_SoA.swift:801–840), unlike the preconverted reduced paths. This is a concrete conversion-boundary difference, not a measured performance conclusion.

Profile fields (68–78): strategy; workload string; throughput = candidate count / mean elapsed time; mean/P50/P95/P99 latencies; **estimated** memory footprint; synthetic accuracy score; timestamp. Percentiles (378–386) use clamped `Int(iterations*p)` as a zero-based index, despite the nearest-rank comment. No dispersion, sample count, hardware, version, operation or conversion-boundary metadata is retained.

`estimateMemoryFootprint` (682–707) computes FP32 `(N+1)*D*4`, mixed `D*4+N*D*2`, INT8 `(N+1)*D`. These are scalar payload estimates, not measured peak memory/allocation/RSS: they omit simultaneous synthetic representations, result arrays, SoA conversion/padding and INT8 parameters. The line 390 “Measure memory footprint” comment is misleading.

`measureAccuracy` (710–737) uses production AoS Float dot output as reference, computes average `abs(Double(result-truth))/max(abs(Double(truth)),1e-6)`, then `1-min(meanError,1)`. Subtraction occurs in Float before Double conversion. This is a bounded synthetic mean-error score, not worst-case accuracy or independent high-precision truth; empty data/error returns zero accuracy. Selection uses a weighted quality score rather than enforcing an accuracy threshold.

## Invalid inputs and persistence

`score` (80–97) checks only positive throughput/mean/memory before logarithms; accuracy is not validated, and percentiles/timestamp are not checked or used for selection. Decodable finite but invalid records (negative/out-of-range accuracy, incompatible strategies, mismatched workload fields, nonsensical percentiles) are not rejected semantically. Ordinary JSON decoding rejects nonconforming float tokens by default, but that is not semantic profile validation. A list with only invalid negative-infinity scores still has a max element and can yield its strategy.

Supported-dimension negative batch sizes reach `0..<batchSize` in generation (623/642/661). Negative warmupIterations reaches `0..<warmupIterations` (340). Only iterations<=0 is explicitly rejected (337), **after generation already happened**. Large counts incur allocation/work before unchecked payload arithmetic (693/698/703); these are source-derived hazards, not reproduced crashes in this review. Zero batch selection is tested; zero profiling yields throughput and accuracy zero rather than a meaningful profile. Invalid/nonfinite latency constraints are merely stored and ignored.

Private initialization (135–155) selects implicit Application Support/VectorCore/kernel_profiles.json, unless disabled by environment/process detection. Its URL parameter cannot be supplied by a normal public or @testable caller because the initializer is private. Disabled persistence and disabled profile selection share detection of XCTestConfigurationFilePath, CI/GITHUB_ACTIONS/TRAVIS presence, bundle identifier containing Test/test, process name containing xctest, or VECTORCORE_DISABLE_TUNER_CACHE=1 (143–152 and 199–205). The comment mentions SWIFTPM_PACKAGE_DEPENDENCIES, but code does not inspect it. Detection is evaluated at init for persistence and again per selection for profile use; explicit cache disabling also skips in-memory profile selection, not just disk.

`ensureProfilesLoaded` (159–163) runs only from selectStrategy. `profileWorkload` can therefore save an initially empty-cache subset before any existing profiles were loaded, overwriting other on-disk workload records. This is an additional order-sensitive source path to cover in ordinary persistence tests. `loadProfiles` (760–771) decodes the bare dictionary wholesale, with no version/hardware/age/key validation; failure prints and leaves current state. `saveProfiles` (774–789) writes that dictionary atomically and prints errors. Overrides are never serialized despite line 224's restart-persistence promise. Public calls do not surface persistence errors.

## Existing tests and ordinary-path gaps

KernelAutoTunerTests covers heuristic modes/dimensions, same-process override, profiles at all widths, synthetic accuracy, payload formulas, a normal score and zero-throughput score, unsupported-dimension profiling, zero-batch selection, key equivalence and strategy counts. It does not cover resource constraints, nonfinite/negative inputs, ordinary disk roundtrip/provenance, stale profile rejection, explicit mixed full mode, or restart overrides.

The three memory-estimate tests (262,289,315) are synchronous XCTest methods that launch unawaited Task bodies; their completion/assertion association is not guaranteed by those test methods. `testWorkloadHashConsistency` (412–432) installs an override without removing it, unlike testManualOverridePersists. Ordinary persistence cannot be exercised at an explicit temporary URL through the current private initializer. CI/test bypass means existing selection passes cannot establish persisted-profile selection behavior. A future design needs a deliberate testability decision and separately controlled ordinary environment; this inventory chooses no new API and ran no probes.
