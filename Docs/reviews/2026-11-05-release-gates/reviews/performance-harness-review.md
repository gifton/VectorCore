## Reproduced findings

Nonfinite diagnostic numbers are represented by explicit tagged objects in that strict JSON file; the reproducer constructs actual Python NaN/Infinity values. The retained input snapshots are authoritative if the working helper changes during remediation.

1. **Empty process inventory admits.** `parse_ps('PID TIME COMM\n')` returns `{}`; five otherwise healthy frames with that inventory produce `ready=true`. Missing process evidence therefore becomes no contention/compiler evidence. Reject empty inventories and require the observation's known process identity/schema; do not invent a universal claim of complete process visibility merely from one nonempty row. Malformed headers, bad rows and duplicate PIDs already throw, but their controls miss the empty-success case.
2. **Invalid numeric telemetry admits.** Synthetic NaN monotonic timestamps, infinite final monotonic time, NaN process CPU seconds and NaN host idle ticks all produce `ready=true`; threshold comparisons with NaN are false. Negative cumulative process CPU values also admit when their deltas are positive. Boolean `false` as `thermalStateRawValue` is accepted as numeric zero. Require strict types and finite/range-valid values at the schema boundary: unsigned 32-bit integer CPU ticks (not booleans/floats), finite nonnegative CPU seconds, finite ordered observation times, an actual integer thermal enum and actual Boolean low-power state. Validate derived deltas/percentages too. `cpu_seconds` should reject nonfinite overflow and impossible clock components instead of allowing malformed syntax to become valid evidence. Missing `thermal` currently raises `KeyError`, preventing a success result; retain that fail-closed outcome, preferably with a structured invalid-admission record.
3. **Recorded cadence is not validated.** Five synthetic frames spanning only four milliseconds produce `ready=true`. `evaluate` checks only `elapsed>0`; it never checks the five-frame nominal schedule or the actual capture interval. The live collector targets fixed starts, but a delayed frame can trigger immediate catch-up captures. Validate finite per-frame timing, accepted start jitter and intervals, total observation window, and nonoverlap/capture duration. The owner reports coordinator-approved refinement: nominal starts 15 seconds apart, actual start in [target,target+1s], interval 14…16s, no overlap. That refinement should be recorded and tested rather than silently inferred from the old rule.
4. **Process interval and host interval are not the same capture.** The collector stamps `monotonic` and host ticks before invoking `ps`, then invokes thermal/power tools serially. Process CPU deltas are divided by the difference between those frame-start times. If `ps` capture delay differs between frames, the numerator covers a different interval and can understate or overstate the process rate. Retain process-capture start/end times and derive its own paired interval (with an explicit midpoint approximation or conservative uncertainty bound); reject excessive span/skew. `captureElapsedSeconds` was retained but unused by the initial evaluator. This is a source-derived finding, not a measured host timing failure; the preflight frame's total capture span is only 0.1693s.

These are repeated instances of a malformed-observation admission class, not isolated fixture exceptions. Regression coverage should exercise each field and boundary, including missing/empty data, booleans masquerading as integers, NaN/±Infinity, negative/oversized counters, zero/backward times, bad cadence, overlapping spans and before/after pair identity changes. A fix only for the first empty dictionary would not close the class.

## Process identity, churn and exclusion scope

The initial code excludes **no observer PID from percentage checks**; all comparable observed processes are conservatively counted. It separately rejects a hardcoded set of compiler/test executable names, `.xctest/` paths and `VectorCorePackageTests` names. The recognized `swift-frontend` control correctly returns `ready=false`. An arbitrary executable named `unknown-suite-runner` is not recognized, so the source supports **listed-name detection plus coordinator work suspension**, not automatic proof that every possible compiler/test workload is absent.

It compares per-process cumulative CPU only when PID and executable string match both endpoints. Processes appearing/disappearing or changing executable are silently omitted from percentage evaluation. Two synthetic cases retain this behavior: a one-frame process and a PID with a changed executable both admit despite their large cumulative CPU record. A large cumulative value alone cannot reveal when that process consumed CPU; these examples establish omission/unknown status, not an interval rate. PID reuse with the same executable can also evade identity matching if its new counter is not smaller. The existing negative-delta rejection handles only one reuse symptom.

The rule already acknowledges start/exit omissions and that whole-host CPU deltas include their work. That is a useful limitation, but host idle ≥90% does **not** enforce a 25%-of-one-core cap for every short-lived process on a multicore machine. Record churn/noncomparable identities explicitly, strengthen identity with available start-time metadata where practical, and either reject unknown intervals conservatively or bound the rule to comparable observed identities. Do not claim a universal no-process-contention result. Brief compiler/test work entirely between frames cannot be excluded by snapshots; scheduling coordination remains necessary. There is no recommendation to kill unrelated processes or broaden computer permissions.

Whole-host idle based on deltas of the four Mach CPU-state counters, including 32-bit wrap handling and rejecting an unchanged interval, is the correct kind of **interval** quantity. The synthetic 70%/90%-wrap controls pass. Process cumulative CPU deltas divided by elapsed wall time represent percent of **one core**, not a host-normalized percentage or instantaneous CPU. This distinction is correctly named in the helper. Neither metric reports frequency, core placement, per-core headroom or temperatures.
