# E04 preliminary ownership inventory

Root source inspection at accepted Core source0dbb18c (documentation HEADbce6c8b),2026-09-22. This is not an approved implementation brief, runtime reproduction, performance profile or closure. E04 still requires a concrete ownership/initialized-element contract before dispatch.

## Existing surfaces

- SwiftBufferPool is a public actor implementing BufferProvider. It stores cached raw addresses, tracks active UUIDs without their allocation metadata, and has an empty deinit. Release trusts the supplied handle's size/pointer after UUID removal. currentUsageBytes measures active rounded bytes; cached bytes are recomputed by cleanup, which only removes entries older than60seconds. It therefore does not enforce the configured cache cap on a fresh return burst. nextPowerOfTwo can overflow, and configuration/request domains are not validated before arithmetic/allocation. Linux aligned_alloc also needs size/alignment compatibility considered. No Core production use of Operations.bufferProvider was found in the inspected call inventory.
- Operations/BufferPool is an internal actor; TypedBufferPool<Element> is public. Both cache bare typed pointers and lack destruction cleanup. BufferPool's currentMemoryUsage mixes active and cached bytes, clear resets it while outstanding buffers can later return, and acquisition-time eviction cannot enforce a return-time cache budget. Neither raw-return interface carries a unique lease generation or initialized-element count. BufferPoolContext explicitly releases on success/throw, but its async bodies expose unsafe buffers; cancellation is cooperative and pointer nonescape remains a caller obligation.
- Public BufferHandle is copied id/size/address metadata. Sendable does not make the pointee synchronized or keep the provider alive. BufferProvider's await-in-defer example does not compile. API-37 calls for a compiling scoped/do-catch path that retains the provider through completion and releases once on success/throw/cancellation. The contract must distinguish clear (active handles remain valid) from owner destruction; a public owning-handle redesign has not been selected.
- MemoryPool already has tested synchronous lock bookkeeping and weak-pool handle fallback ownership. A handle can outlive its pool and free its own allocation, unlike a borrowed BufferProvider handle. Preserve that supported behavior. Generic raw storage has no tracked initialized-element count: callers must initialize/deinitialize nontrivial values before returning/deallocating, unless a deliberately designed initialized lease is added. Existing trivial Float tests cannot prove generic element lifetime by themselves.
- Root follow-up inspection: ExecutionOperations.OperationContext.withTemporaryBuffer releases via `defer { Task { await bufferPool.release(buffer) } }`, so release can occur after the helper returns. E04 should include that narrow helper and require awaited release on success and throw, including cooperative cancellation. A detached cleanup task is not evidence of release-before-completion.

## MemoryPool work requiring design

The cached-byte admission predicate already uses subtraction and stride correctly, but each return materializes flatMap arrays under the lock. API-32 is a profiling opportunity, not a proved contention bottleneck. Retain a Release allocation/contention profile before deciding whether to replace the scan with a maintained counter; do not infer a latency gain from source inspection. Any counter repair must cover every cache removal/reuse/return/cleanup/destruction path and all type/size buckets.

EX-05 fallback still multiplies count*stride unchecked, downgrades requested alignment to natural alignment and assumes binding on fresh memory. O04's common allocator repair does not reach this last-resort branch. MemoryPool's power-of-two helper can return a capacity below an enormous requested count once doubling stops, and negative counts are not rejected before handle construction. A future E04 brief must resolve invalid request/configuration behavior, checked bucket/byte arithmetic, zero-count allocation semantics, actual guaranteed alignment, fallback injection and matching deallocation. Forced allocation failure can be tested; real OOM recovery must remain qualified.

## Required decisions before dispatch

1. Choose ownership of checked-out versus cached allocations in all three actor pools, including teardown with live handles, explicit release, duplicate/foreign handle treatment and generic initialized-element duties. Preserve existing protocol clear semantics. Do not promise safe pointer escape or concurrent pointee mutation.
2. Define active/cached/peak statistics separately, with strict return-time cache-byte caps and zero-budget behavior. Decide how existing trackStatistics=false affects operational counters versus observable statistics; do not silently leave an advertised knob undefined.
3. Define request/config validation and overflow behavior at throwing versus nonthrowing surfaces, including power-of-two rounding, alignment, byte products, MB conversion and zero counts.
4. Specify counted real-allocation/free evidence (empty/returned/clear/destruction/live-handle cases) and nontrivial initialized-element controls separately. Generic actor raw-buffer use must compile under actual Swift6 isolation rules; do not solve that by suppressing concurrency checking.
5. Retain the standalone MemoryPool regression's saturation/lifetime/retention/cleanup checks; investigate any test fixture binding/initialization assumptions before changing the existing counted allocator driver. No optional allocator gate or GPU execution is authorized by this inventory.
