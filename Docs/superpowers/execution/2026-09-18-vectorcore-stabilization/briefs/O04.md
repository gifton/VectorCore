# O04 — Alignment, binding and initialized copy destinations

Root-approved contract. Dispatch after S01 is accepted. OWN-08/OWN-09/OWN-11 closure candidates; OWN-25 remains an investigation until injected-failure evidence. Breaking changes authorized. No normalization-range, allocator budget, concurrency or performance-target claim.

## Pointer normalization

Support every naturally aligned Float pointer, including offsets0/4/8/12 from a64-byte allocation. SIMD16-byte alignment is optional. Replace every SIMD load in the public pointer overload with loadUnaligned (or an equivalent reviewed scalar gather); cover all three passes and unrolled/tail sites. Raw storeBytes of trivial SIMD values supports these Float-aligned destinations; retain binding to the Float owner. Dimension0 performs no access. Require dimension>=0 explicitly before the zero return; negative dimensions reject with a count diagnostic. Capacity/lifetime/nonzero finite supported input remain caller contracts. Do not change scaling, sum accumulation, zero/nonfinite handling or optimized-wrapper numerical behavior here: N01 owns those defects. Correct adjacent pass-count/alignment documentation without claiming arbitrary-range stability.

Independent ordinary-value oracle: Double sum of squares for moderate alternating nonzero coordinates, normalize independently, require finite outputs and near-unit norm with a justified Float tolerance. Offsets0/4/8/12 × dimensions0...5,15...17; also dimensions31/32/33 to cover repeated unrolled groups. Prefix/suffix sentinels must remain exact. Baseline Debug misalignment traps run in children; retain the audit qualification that Release happened to succeed on the audited ARM host. Do not manufacture a Release failure claim.

## Owned SIMD storage and conversions

All four optimized FP32 array constructors must stop assuming a Float-array base meets SIMD4 alignment. Build each SIMD4 value from four scalar elements (preferred simple implementation), or use loadUnaligned on the source raw pointer without rebinding the Float owner. No public helper/API needed. Preserve S01 backing storage/count guards and inlinable visibility.

Vector384's toArray/read/mutable borrows must use the same scoped SIMD4<Float>→Float strategy as the other widths. The SIMD owner has its type's natural alignment; Float requires no stronger alignment. Use withMemoryRebound inside the owning ContiguousArray borrow, capacity measured in Float elements. Do not use the original SIMD pointer during the rebound closure and do not retain any pointer beyond its borrow. Throwing exits restore binding. Caller-provided closures remain unsafe-borrow APIs with explicit nonescape/lifetime obligations; arbitrary return values cannot be mechanically prevented from hiding a pointer.

The reviewed type/layout model is specifically homogeneous SIMD4<Float> as four contiguous Float lanes, not arbitrary generic aggregates. Verify size/stride/alignment assumptions and all-width constructor→SIMD access→toArray→read borrow→mutable borrow→SIMD access→COW round trips in Release. Include throwing immutable/mutable closures, exact error identity, persisted writes, source Float-array reuse and retained vector-copy independence. Review every typed-owner bind/rebound site across these four files; a spelling replacement alone is not proof. No optimizer miscompile has been reproduced for OWN-09.

Primary language references: [Swift binding migration guide](https://www.swift.org/migration-guide-swift3/se-0107-migrate.html), [SE-0333 scoped rebound](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0333-with-memory-rebound.md), [SE-0349 unaligned loads/stores](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0349-unaligned-loads-and-stores.md). Root interpretation: copying scalar lanes avoids the stronger alignment needed when rebinding Float input to SIMD; scoped borrowing of the aligned homogeneous SIMD owner restores its binding. No package/toolchain floor increase is needed (both proposals implemented in Swift5.7).

## alignedCopy destination state

Choose one contract: destination already contains count initialized T values; source contains count initialized T values; both are naturally aligned, valid and nonoverlapping. Copy updates/replaces destination elements, releases old destination values and retains copied values. It does not initialize raw storage. Use destination.update(from:count:) uniformly; remove alignment-dependent initialize/update branches. Keep the public signature including preferredAlignment for source compatibility, document that this hint does not select a different ownership operation or promise a measured optimization. Require count>=0 and preferredAlignment>0 before any work, including count0; a clear nonthrowing precondition diagnostic is sufficient. No overlap support or new initialize API. Migration: callers with uninitialized destinations use the standard pointer initialize(from:count:) operation themselves.

Test class weak/deinit sentinels and a nontrivial value containing reference/String/Array members at preferred64-byte alignment and natural-only offsets, source/destination independently offset. Initialize every destination before calling. Verify old destination objects die exactly once, source/copy lifetimes persist correctly, count0 does nothing, final content exact, and all owners eventually release. Do not use an uninitialized-destination crash as RED. Invalid count/hint tests run in bounded children. Free isAligned and both AlignedMemory.isAligned overloads return false for nonpositive boundaries, avoiding modulo-by-zero; positive boundaries retain address-multiple semantics (not restricted to powers of two).

## Allocation contract and fallback investigation

Root expands scope to AlignedMemory.swift because the common allocator creates the pointer used by the repaired fallback and must establish its binding. allocateAligned<T> returns bound-to-T, uninitialized storage; caller initializes/deinitializes its logical count and releases with AlignedMemory.deallocate/free. Keep power-of-two and minimum16 alignment preconditions; also require alignment>=MemoryLayout<T>.alignment. Negative count or count×stride overflow throws VectorError.invalidDimension before any allocation. Count0 returns a nonnull aligned allocation for one element, while logical count remains0; callers must not infer an extra initialized element. Use checked arithmetic and bindMemory for newly allocated raw storage. Allocation failure remains the existing allocationFailed error.

All four AlignedDynamicArrayStorage public constructors share one allocation path. Validate nonnegative dimension, representable byte count and allowed alignment before choosing an allocator; nonthrowing constructors reject invalid arguments with explicit diagnostics. If primary aligned allocation fails, Swift raw allocation requests the SAME alignment and the same checked size (at least one Float for count0). Bind fresh raw memory to Float. Preserve a matching deallocation record: posix→free; Swift raw→raw.deallocate. Report the requested alignment only because both selected paths supply it. Swift fallback allocation can still terminate for actual exhaustion; this is not a recoverable-OOM API or an allocation-budget design. Preserve initialization values, borrowed counts and reference-class semantics.

Use a narrow internal per-call primary-allocation injection seam, with no mutable global hook, production flag or public initializer parameter. Public constructors route through the shared helper. Tests force primary failure through that helper/appropriate internal construction route and exercise resulting storage initialization/use/destruction. Test all public constructor controls, logical counts0/1/3/17/257 and requested alignments16/32/64/256/4096. Verify returned pointer modulo requested alignment, guaranteedAlignment, verifyAlignment and values. Verify the injected primary was called once and fallback metadata selects the Swift deallocator. A deterministic fallback allocator seam may be used only to observe requested alignment/deallocator pairing, not to return a pointer that violates the new request. Distinguish this forced-failure validation from a real OOM reproduction. If the old fallback happens to be aligned, record that fact; the original concern was a weaker requested guarantee, not previously observed corruption.

Generic allocator tests use Float, SIMD4<Float>, a naturally higher-aligned SIMD type if available and a reference-bearing value, with correct initialize/deinitialize/free lifetime. Negative/overflow counts fail without requesting huge memory. Invalid alignments in bounded children; do not attempt huge allocations. Inventory callers of allocateAligned and confirm the bound/uninitialized contract is compatible. Do not broaden into MemoryPool/AlignedValueStorage ownership fixes; report any separate concrete concern to root.
