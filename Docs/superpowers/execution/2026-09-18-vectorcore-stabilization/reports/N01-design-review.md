# N01 independent design review

Scope: early ruling and route-policy refinement in DESIGN_DECISIONS.md; historical N01; NUM-01/NUM-02/API-39; bounded normalization/division source context. This is a design review, with no source changes, builds, correctness closure, or downstream inspection. Root retains policy decisions.

## Mathematical assessment

The proposed FP32 arithmetic has sufficient range. A finite Float is exactly representable in Double; its square has at most 48 significant bits, lies below 2^256, and the smallest nonzero square is 2^-298, above Double's normal floor. Even Int.max positive squares sum below 2^319 on a 64-bit host. Thus accumulation, square root and division can stay in Double without a Float norm or reciprocal. Exact squares do **not** imply an exact sum: compensated accumulation or a justified alternative remains necessary. Round only final coordinates/magnitude/squared magnitude to Float; returning infinity for an actually unrepresentable Float magnitude is compatible with successful normalization.

For Double, divide by the positive finite maximum, accumulate squared scaled values, and divide scaled coordinates by sqrt(q). Since 1 <= exact q <= count, the q range is safe for ordinary Double/Int counts. Intermediate underflow can discard extremely small coordinates; the contract should bound absolute/normwise error, not promise relative accuracy or strict sign alignment for every nonzero coordinate. Signed zero from negative underflow should follow native arithmetic. Never form an original-scale dot product in the direction test: it can overflow.

"Native scaled fallback" alone is not a range proof for every BinaryFloatingPoint conformance. Float16 needs widening, including when count exceeds its finite range; a hypothetical wider-significand/narrow-exponent custom scalar can have the same q overflow issue. Root should qualify supported formats or require an exponent-aware accumulator for that generality. At minimum, no unconditional conversion of Double-or-wider values to Double, and a custom Double-backed conformance must exercise protocol defaults. Where available, Float80 can expose precision narrowing; absence on arm64 must be recorded, not treated as coverage.

## Decisions/route gaps to settle in the brief

1. **TransformOperations owns independent numerical code.** Its serial and parallel bodies compute a Float magnitude, replace magnitudes <= leastNormalMagnitude (also NaN) with zero, and divide by possibly infinite magnitude. Public Array.normalized() async reaches this path; Operations.normalize reaches the permissive array provider. Reserve writes and explicitly choose the two public batch APIs' zero/nonfinite behavior and error behavior. Consumer tests alone cannot repair TransformOperations. Exercise both sides of its existing parallel threshold without changing that gate.
2. **Exact tolerance semantics.** Specify `abs(norm - 1) < tolerance` versus `<=`, and norm rather than squared-norm residual. Preserve existing strict inequality if compatibility is intended. Validate finite/nonnegative tolerance before all early returns; test negative zero, NaN, infinities, zero, boundary-adjacent values, and a large finite tolerance. A finite input whose norm exceeds Float range still needs a reliable decision. Vector.normalized(tolerance: Float = 1e-6) competes with checked normalized(): fixtures should explicitly bind `Result<..., VectorError>` and separately call the tolerance overload.
3. **Failure observation.** Fix operation name and reason policy for empty, signed-zero-only and nonfinite checked input, including precedence when several invalid properties occur. "Unchanged" for permissive NaN input and failed mutation is best tested with element bit patterns, not floating equality. Pointer dimension 0 should access nothing; specify dimension < 0 separately. Test unchecked preconditions in Debug and Release subprocesses; normal preconditions do not promise behavior under `-Ounchecked`.
4. **Representation and hints.** Built-in INT8 exclusion from IndexableVector is sound, but generic VectorProtocol normalization also serves representations that can quantize writes. Scope unit-vector claims to representations that preserve output scalars; do not accidentally extend them to INT8 or arbitrary custom lossy conformers. NormalizationHint checked/unchecked conveniences set true immediately after normalization; test actual built-in outputs and clarify the custom IndexableVector conformer's obligation. Known-unit constructors remain assertions. Auto-detection's existing 0.001 metric differs from Vector.isNormalized's squared-norm 1e-6 and should not silently become one shared tolerance.
5. **NormCache has two different concerns.** buildNormalized_* consumes checked normalization and preserves any failure input, so it can retain nonfinite vectors. Its preNormalized helpers then use min/max clipping, which needs a finite-input obligation or explicit separate ownership for invalid inputs. Ordinary NormCache builders independently compute Float dot/sqrt; their cosine helpers square cached Float norms again. Repairing normalization does not repair those magnitude/cosine routes. Explicitly defer that wider distance range work rather than claiming cache safety.
6. **Matrix propagation.** The current ternary distance clamp preserves NaN; retain that property. Exercise invalid query rows, invalid prepared candidate rows, invalid-versus-zero, mixed valid rows, and both prepared/unprepared entry points through actual GEMM. Verify invalid rows do not contaminate unrelated valid pairs. Packing/dimension semantics remain R03; fixtures must use already-supported Float layouts. NaN row filling alone is not an end-to-end propagation test.

## Independent fixtures and finite-aware tolerances

Use two complementary references, independent of the production helper:

- Closed forms: one nonzero coordinate must produce its signed unit basis vector; four equal-magnitude nonzero coordinates produce exactly +/-0.5. Use least subnormal, least normal, powers of two across exponent range, and maxFinite as common scales. Pythagorean `[3a,4a]` has direction `[3/5,4/5]` when those inputs are exactly representable; choose power-of-two `a` that keeps both finite, including tiny and large regimes. Append zeros to cover tails and fixed widths. These tests isolate scale cancellation without recreating the algorithm.
- Retain high-precision fixtures for uneven/mixed extreme Double inputs. Generate exact Decimal values from binary64 bit patterns (or exact integer significand times a power of two), compute sums of squares and square root at 2500 decimal digits, then repeat at 3000 digits and require identical rounded binary64 expected outputs. Retain generator, input bit patterns, expected bit patterns, precision settings and stability check. Include maxFinite beside least subnormal, mixed exponents, signed coordinates, values adjacent to normal/subnormal boundaries, and cancellation-free unequal patterns. This is offline fixture generation, not a runtime dependency or workload assumption.

Before residual arithmetic, assert expected and actual coordinates are finite, lengths agree, and expected norm is positive. For the explicitly enumerated test dimensions (up to 1536), proposed acceptance is norm residual <= 8 * Float.ulpOfOne for Float and <= 32 * Double.ulpOfOne for Double; coordinate comparison against independently rounded expected values uses <= 8 ulps (Float) or <= 16 ulps (Double), with absolute allowance of the same number of least-subnormal units near zero. Require exact signed-zero classification for direct scalar division. These are proposed regression thresholds, not a universal forward-error theorem; root should adopt or revise them alongside the chosen accumulator.

Compute Float output residuals in compensated Double arithmetic. For Double extreme fixtures, verify residuals in the retained high-precision generator or independent high-precision test reference; do not reuse production scaling. Compare the full output to the oracle (and optionally a finite bounded dot of unit oracle/output with positive alignment), so a wrong unit direction cannot pass norm alone. Include permutation and power-of-two scale variants, while avoiding any assertion that input underflow/rounding preserves the original mathematical direction.

API-39 remains staged: Core fixtures and Core hint behavior can be assessed here; actual pinned VA CPU fallback parity and optional GPU evidence remain separate, unverified work.

## Proposed brief disposition

Reviewed briefs/N01.md after root incorporated this review. The proposed policies resolve the material route/representation gaps: both TransformOperations bodies are owned; S02 separately owns Operations.normalize factory propagation; strict norm-based tolerance and failure precedence are explicit; native-q failure and output-fidelity qualifications bound generic promises; hint conveniences validate returned coordinates; preNormalized helpers propagate nonfinite dots while ordinary NormCache range work remains deferred; matrix prepared/unprepared propagation and independent fixtures are explicit. No architectural contradiction or unsafe implementation requirement was identified in this bounded read-only review. Prerequisite acceptance and implementation evidence remain outstanding; this is not correctness or dispatch-readiness acceptance.

The final acceptance clarification is resolved in briefs/N01.md: uniform norm/oracle-coordinate thresholds apply only when normalization executes. Permissive no-ops and tolerance early returns instead require unchanged coordinate bits and the specified return predicate, explicitly including default fast near-unit and large-tolerance returns. No outstanding concrete design contradiction was identified within this final review scope. Implementation, numerical evidence, and S02/O04 prerequisite acceptance remain separate requirements.

## Scoped safeNormalized addendum review

Reviewed only the N01 route-inventory addition, single-method ownership and 32-option regression requirement, together with current Vector.safeNormalized, Vector.handleNonFinite and NonFiniteHandling definitions. The proposed preprocess-then-normalize policy is consistent and implementable within the reserved method. No concrete design gap was identified.

The independent option oracle must retain these distinctions already specified by the addendum: strict handling examines the original input and throws the existing category-specific NonFiniteError (including original indices) before either propagation or replacement; propagateNaN fills all coordinates only when an original NaN exists; infinity alone does not activate that propagation branch. Replacement flags apply independently by sign/type. Any unresolved nonfinite coordinate prevents normalization of the entire handled vector, so both replaced finite lanes and untouched nonfinite lanes remain as handled. A handled finite nonzero vector normalizes under every flag combination; zero handled input takes strict zeroVectorError before propagate all-NaN before unchanged signed zeros. For example, propagateNaN plus infinity replacement can normalize an infinity-only vector, while the same flags with an original NaN return all-NaN. These cases fit the prescribed all-32-combination scalar oracle.

Replacing infinities with signed finite extremes before normalization intentionally changes the former magnitude/safeDivide composition, as the brief records. NaN-only replaceAll yields zeros; NaN plus finite nonzero coordinates under replaceAll yields a normalized finite vector. Bit preservation applies to returned handled data, not necessarily original input after requested replacements or all-NaN propagation. Numerical unit/oracle thresholds apply only to the finite nonzero normalization branch; unresolved-nonfinite and zero branches require policy assertions instead.

Ownership remains safeNormalized body/docs only. Existing handleNonFinite, NonFiniteHandling, safeDivide and N02-owned safeLog remain unchanged. This disposition records design consistency only; no source changes, builds, numerical execution or implementation-acceptance claims were made.
