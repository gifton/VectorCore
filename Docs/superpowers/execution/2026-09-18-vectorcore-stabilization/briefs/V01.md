## Root-approved contracts and architecture

### Validation is distinct from numeric error

`Correctness.scalar` and `.vector` must represent whether a meaningful comparison was performed independently of its numerical error statistics. Root approves an explicit valid/invalid status with reason, and optional numerical fields for unavailable statistics in serialized output. Keep all valid finite comparisons' measured errors; never represent a failed/unperformed comparison as zero error.

For this benchmark's finite-input reference contract:
- A scalar pair is valid only if both observations and every reported error statistic are finite.
- Vectors require equal, positive lengths and finite compared values/statistics. Both length-mismatch directions are failures; two empty arrays are unvalidated, not a passing comparison.
- NaN and either infinity invalidate the comparison, including equal infinities and two NaNs. This is the benchmark's reference-domain policy, not a new numerical library policy.
- `samples` counts meaningful comparisons. Status/reason and unavailable fields must survive JSON encoding/decoding as ordinary JSON, with no NaN/Infinity number literals or fabricated perfect error.
- Nonfinite/negative threshold overrides are invalid CLI configuration and must produce a nonzero result rather than disable checks.

Strict correctness requires valid evidence for every selected result, positive sample count, and passing finite thresholds. `correctness == nil` is a violation. Non-numerical cases lacking validation are not silently exempted; strict mode may reject them with a clear missing-validation reason. An empty selected result set cannot satisfy strict correctness (full registry/filter repair remains V02).

Retain existing per-case finite thresholds and override meanings. Root does not approve widening tolerances. Threshold failures return nonzero under `--strict-correctness`; execution/provider errors and requested artifact-write/encoding failures return nonzero regardless of strict mode.

### One production path for reporting and process status

Refactor the CLI orchestration enough to return an `Int32` exit status from a reusable internal runner; the `@main` entry delegates and exits with that value. Root approves injecting the suite registry/results into that normal orchestration boundary for tests. Do not add hidden production CLI flags or environment switches that fabricate benchmark outcomes, and do not copy production validation logic into a test fixture.

Write valid success/failure artifacts before returning strict failure when an output destination is usable. I/O failure is necessarily reported to stderr/nonzero even when no artifact can be written. JSON and CSV write catches cannot swallow the error. Invalid numeric timing/report statistics must fail clearly rather than return success; for cases whose computation failed, keep timing absent/explicitly failed rather than generating throughput from zero duration. Exact model representation is implementer-local provided this observable contract holds.

### Batch failures must survive warmup and measurement

BatchBench currently uses `try?` around provider work in many width/metric routes. Root approves making `Harness.warmupAsync` and `measureAsync` accept throwing bodies and `rethrows`, then propagating to a suite/case boundary that produces an explicit failed result. Retain the original case identity and error reason. Cover warmup, calibration, fixed iterations, and recursive multisample calls; none can convert provider failure into a plausible timing/result. A small generic provider-execution helper may be used across width families to allow an injected throwing provider test without changing production provider selection.

No guessed numeric output or successful independent verification may erase an earlier provider failure. Error handling should retain other cases where practical; a suite-level failure is acceptable only if it explicitly identifies aborted work and causes failure, never success. Avoid a sweeping library rewrite.
